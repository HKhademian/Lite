# Agent Handoff: LiteScript language-design review

> **Historical review log.** The original review plan and its todos are complete. Current rules live in [the decision ledger](decisions-and-open-questions.md) and the concept pages; entries below record review history rather than live status. Do not implement a compiler from this log alone.

## Mission

Selected tuple/array clarification, 2026-10-24: [tuple and array shapes](tuple-array-shapes.md) records type-level label replacement in place, fixed tuple-type input construction, homogeneous array tails in callable and ordinary tuple schemas, and fixed-array/fixed-tuple spread construction. ...rest: T checks each additional input as T, including tuple-valued T; the collector is an array, not a tuple specialized to call arity. Rest arrays may have static or runtime-known length. Fresh known-size literals infer [T; N], superseding List-by-default; mut/var remain explicit and do not choose family/extent. Rest access and retention are now selected: readable access by default, no mandatory heap allocation, valid backing storage for borrowed uses, and explicit copy/ownership operations for independent owned storage. Retention requires lasting ownership or a proven lifetime; do not silently repair invalid escape with copying or heap promotion. Writable rest needs an explicit contract and caller permission. Keep runtime-array/copy-operation spelling (the earlier ellipsis was a placeholder), complete ownership/lifetime and mutation-observability rules, allocation/failure policy, general length proofs and spread/default interactions, empty/unresolved-element literal inference, and tail normalization open. The guaranteed contract is the statically known input tuple shape; supplied arguments must provably satisfy its required fixed slots, routing, final-slot types, and access permissions. Runtime tail length does not change tuple shape. Both max(...fixed, ...extra) and max(...extra, ...fixed,) are valid for Int sources when fixed: [Int; 5] proves sufficient total length for the two required inputs. Route the composed positional sequence in written order; the leading runtime spread can supply fixed-slot values when all possible types/access are compatible. Value origins may vary with runtime length; input tuple shape does not. Reject unproven fixed coverage without a runtime arity fallback. The future nonempty call syntax permits optional leading/trailing boundary commas with no argument meaning: max(, ...extra, ...fixed,) supplies the same entries. Do not infer omitted slots, Unit, or defaults from these commas; empty-list variants remain open. Two-colon headers and removing existing headerless/whole-pack literals were explored, not selected. Use a space after fn.

Tuple construction clarification, 2026-10-24: [destination tuple types](tuple-array-shapes.md#construction-guarantees-the-destination-type) are statically guaranteed when the whole supplied composition proves the fixed-slot and array-tail contract. Which source supplies each slot's value may depend on runtime lengths; the resulting type/shape does not. [Rest-only tuples](tuple-array-shapes.md#rest-only-tuples-need-no-fixed-components) with zero fixed components plus a homogeneous array tail are valid: b := (...extra) for an established runtime-sized T array infers that shape without a destination. Do not reject this merely for lacking a known array length or invent a fixed prefix; the later default-label rule supplies rest as its member name. The user's (...(), ...rest) describes empty prefix plus tail; full compatibility with explicitly named tails, bare-array equivalence, normalization, and full recursive syntax remain open.

Rest element inference, selected in the 2026-10-24/25 discussion: [colon-only rest declarations](tuple-array-shapes.md#a-colon-distinguishes-inferred-rest-declarations-from-type-spread) admit c: (...rest:) = (...extra), using the required colon to distinguish the declared tail name from (...Params) type expansion. Infer its element type only from sufficient static initializer/expected-contract information; a compatible fixed source may also populate the explicitly requested array tail. No infer keyword, ordinary dangling name: form, runtime element-type discovery, or new unknown-input callable inference is selected.

Rest label/value construction, selected 2026-10-25: an unannotated inferred rest-only tuple uses the canonical ordinary label rest, independent of its source expression. No new inline call-entry/pattern forms, multi-tail tuple composition, tail-label collision policy, write grants, or ownership machinery are selected. Stored tuple forwarding is selected separately below.

Named array-segment extents, selected 2026-10-25: [segment types](tuple-array-segments.md) use ...name: T for a general array count and ...name: T; C for exactly nonnegative compile-time C elements, exposing [T; C]. Standalone runtime-array spelling, extent inference/compatibility, ownership, and ABI stay separate.

Fixed-array access and tuple repacking, selected 2026-10-25: [literal arr.0 access](arrays.md#literal-numeric-dot-access-selected) is valid for [T; N] with static bounds, the same element/location and permissions as arr[0], and no type identity or runtime-sized dot-access extension. arr.ind remains literal member lookup. Plain stored assignment, label-sensitive compatibility, source-once evaluation, and ownership/access rules remain. General length-fact retention, mixed-label collisions, copying/allocation policy, and array/tuple identity are not selected.

Union element inference and concrete tail extents, selected 2026-10-25: [heterogeneous packing](tuple-array-shapes.md#union-element-inference-and-known-construction-extents) through (...rest:) and known-size nonempty array literals use the normalized union of established contribution types. Per-index static types are the common union, not the original heterogeneous tuple positions. Expected element contracts remain constraints. Empty literals without element evidence, unresolved types, and general API/ownership/effect fact propagation remain open. Treat ...rest[...] as explanatory shorthand only; ...rest = [...] is the unambiguous named-tail spelling.

Tuple shape inference precedence, selected 2026-10-25: [explicit/expected destination types](tuple-array-shapes.md#destination-types-take-precedence-over-inferred-shape) are the reference contract; infer only omitted information. Zero/singleton tuple expansion, selected 2026-10-25: [fixed [Int; 0] spread](tuple-array-shapes.md#zero-and-singleton-fixed-expansion-versus-declared-tails) produces Unit, while fixed [Int; 1] spread produces (:Int,), not a scalar, without requiring a comma in (...arr1). Explicit (...rest = arr0) and (...rest = arr1) retain a declared tail containing zero or one element. The empty tail is not Unit; the one-element tail is not the fixed singleton. Concrete tail extents are retained, and .rest remains available. Equivalent call expansion does not equate stored types or broaden Unit-only patterns. Explicit/expected destination precedence and source-once evaluation still apply; bare-array identity and storage/ownership policy remain separate.

- Selected [conditional guarded updates](conditionals.md#no-final-else-guarded-update), 2026-10-25: a no-`else` conditional is partial; matching branches supply `T`, while no match is noncontributing. Ordered failure tuples use existing tuple syntax: `else e: (: A, : C, : B)` or `else e: (a: A, c: C, b: B)` match exactly that order and bind a real tuple; positional access works in both, labels only in the named form. Individual `:A`/`:B` filters each consume one and both run when both are pending. Clause order is observable: exact tuple, then `&` set, then individual filters, then `!`. Outer receiver parentheses are optional when unambiguous; tuple parentheses remain part of the type. Raw tuple patterns remain ordered. `&` is recovery-pattern notation, not a general type operator; duplicates, representation, and the `&` value's public operations remain open.
