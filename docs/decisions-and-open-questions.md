## Live reads of admitted surrounding bindings, 2026-10-29

- Where surrounding binding access is permitted, a deferred body reads the
  current value of its original lexical binding when it evaluates that name.
  Do not implicitly snapshot it at function creation. = replacement can affect
  later reads of that var binding; := shadowing cannot retarget the reference.
- Ordinary value copies remain copies. A fixed saved := double can freeze the
  eligible callable value deliberately; no capture-header syntax is selected.
- Evaluate each callee once before its arguments. A permitted replacement during
  argument evaluation does not replace the outer call's already selected callable.
- In the var-corrected mixed probe, x1/x2/x3/x4 are 0/4/4/16. Surrounding-access
  eligibility, permissions, storage, ownership, and escaping lifetime rules
  remain open. The initial static safety direction still applies, and private

## Initial static initialization enforcement, 2026-10-29

- Reject evident early calls whose reached body would read an uninitialized
  binding. For the initial supported subset, conservatively reject calls whose
  initialization safety cannot be established as well. Distinguish demonstrated
  invalid access from insufficient proof in diagnostics.
- No runtime readiness-check fallback is selected for that subset. Exact proof
  rules, conditional/indirect callbacks, escaping functions, and the full
  language's long-term policy remain open. Revisit concrete callback cases
  before treating conservative rejection as a universal language rule.

## Lightweight native execution priorities, 2026-10-28

- Lightness is a core design priority: fast native execution, low allocation and memory overhead, fast startup, small runtime support, and small final executables. Ordinary native programs should require neither a VM nor a tracing garbage collector. These are selected goals, not implemented performance or no-GC guarantees.
- Assess execution time, compilation/startup, memory, runtime footprint, and executable/deployment size separately. Specialization/inlining can trade size for speed; required shared-library bytes must remain visible in size accounting. Numeric budgets and target-specific acceptance workloads remain open.
- Preserve selected copy, access, safety, cleanup, and failure behavior. Owned storage with deterministic cleanup, checked views, explicit sharing, static generic specialization, a typed compiler core, C generation, and a later direct LLVM path are recommendations to investigate. No ownership system, implicit move/borrow, backend, ABI, linking mode, freestanding profile, or implementation order is selected.

## Ordinary and advanced memory control, 2026-10-28

- Ordinary code should receive safe automatic storage and cleanup without
  routinely requiring manual allocation/freeing, ownership bookkeeping, or
  lifetime annotations. Preserve selected copy/access semantics and understandable
  contracts for consequential copying, sharing, and ownership changes.
- Advanced memory controls must remain available through an explicit step with
  little ceremony, outside the default beginner surface. A built-in memory-module
  import is an illustrative entry point; no import spelling, module name, API,
  or specific facility is selected. Importing APIs does not itself alter
  unrelated code or remove checks; advanced operations need their own contracts.
- This selects ergonomics within one language. Reclamation, ownership inference,
  borrowing, reference counting/cycles, resource copying, placement, raw memory,
  and cleanup timing remain open. Native execution without a mandatory VM or
  tracing collector remains a goal. No advanced implementation is required in
  the tiny demonstrator or first useful milestone.

## Block order, deferred bodies, and module lookup, 2026-10-28

- Every executable code block, including a run-file body, evaluates reached
  items top to bottom. Ordinary eager code cannot use later bindings; ordinary
  shadowing preserves the order of the earlier and new bindings.
- A deferred function body may refer to later identifiers. Creating the callable
  does not execute that body or move later initialization earlier. The callable
  binding itself is not hoisted. Name visibility does not permit uninitialized
  reads; exact future-shadow selection, recursion, capture mechanics, and early/
  indirect-call checking remain open. In the op/tmp2 probe, tmp2's initializer
  has not run at the read; an initialized value cannot simply be assumed.
- Module declaration lookup should permit safe forward references without
  mandatory manually maintained headers or duplicated signatures. This does
  not select arbitrary import-time execution or runtime initializer reordering.
  Module identity, cycles, cross-file inference, and scheduling remain open.
- Declaration-oriented modules do not rule out compile-time computation or
  metaprogramming. Those mechanisms, syntax, effects, and proof/diagnostic
  policies remain investigations. Safety is required, not an implementation
  result or permission to access an uninitialized value.

## Recapture, Result inspection, and implicit panics, 2026-10-27

- [LP-0016 r1](proposals/LP-0016-recapture-and-warning-policy.md) selects legal recapture: capture(T ! Es) is T ! (Es | Panic), equal to the existing type if Es already includes broad Panic. Preserve stored success/failure occurrences, payloads, origins, multiplicity, and order without re-raising them or adding an outward layer. Deliberately nested successful Results remain data. Type deduplication never deduplicates occurrences.
- Type equality does not prove a redundant boundary: a function returning stored outcomes can still produce a separate live panic while evaluating its call. Never reject/warn solely because capture's type is unchanged. An optional proof-based redundancy warning is suppressible; all warnings are suppressible as a general policy. Exact control syntax/configuration and optional defaults remain open, without changing semantics or required errors.
- [LP-0017 r1](proposals/LP-0017-result-failure-occurrence-patterns.md) selects .err(e) first-occurrence projection as F and .err(...es) ordered all-occurrence collection as [F] for T ! F. Both branch once, no .err pattern matches success, and tag-only .err binds nothing. .ok(value) preserves the complete T. Source inspection changes no stored outcome and performs no hidden propagation or recovery mutation.
- Scalar subpatterns test the first occurrence, not a later matching member; use else filters for category searching. Occurrence internals stay intact. raise e forwards only the bound scalar; raise ...es or outcome! forwards the complete group. This Result-specific collector does not generalize enum constructor rest or tuple-pattern remainder rules. Ownership/providers and physical construction remain open.
- [LP-0018 r1](proposals/LP-0018-implicit-panics-without-effect-declarations.md) prohibits checked live-panic effect declarations or inferred transitive live-panic lists. Bounds/arithmetic/helper faults stay implicit without appearing in every caller signature. Explicit capture exposes newly caught live panics through broad Panic, retaining concrete categories/payloads for matching.
- Literal panic-bearing outcome returns remain first-class data: an ordinary call of fn(): T ! Panic returns T ! Panic, never T with a silently projected effect. The exploratory fn(): T ! SpecialPanic1 implicit-effect interpretation and exhaustive-bound recommendation are withdrawn. This does not ban custom Panic category types/construction/matching. Non-exhaustive documentary known-fault annotations remain under investigation and have no type, compatibility, or exhaustiveness effect; no annotation syntax is selected.

## Early function return from captured recovery, 2026-10-27

- [LP-0015 r1](proposals/LP-0015-early-return-recovery-paths.md) selects ordinary early-return semantics. For tmp1: T ! (ErrA | ErrB | Panic), `tmp2 := tmp1 else :ErrB { return 1 }` returns 1 from the nearest function/closure whenever ErrB matches, even if ErrA/Panic coexist. tmp2 is never initialized on that path; T ! (ErrA | Panic) describes only continuing paths.
- The 1 belongs to the enclosing function's success contract, never tmp2's normal result. It must fit explicit/expected output checking or eligible success inference. The return abandons the unfinished captured recovery. Unmatched categories were not consumed by the ErrB filter, but are not implicitly forwarded or grounds for an additional handling rejection here. There is no hidden forwarding of other stored Result locals.
- Handler-local tagged return is a different completion: finish only that handler and preserve its remainder for the next layer. tmp* traces already explain this distinction. A temporary binding itself does not unwrap anything.
- Applicable cleanup still runs. The abandoned captured remainder is not an active propagating failure carried into cleanup; new payload/cleanup failures follow existing rules and can prevent the normal return. The rejected automatic failure-conversion/remainder-based rejection recommendations are no longer current for plain return.
- Other exit kinds, including raise, failure-directed !, and nonlocal tagged/loop exits, retain their separate unmatched-remainder policy. This decision does not silently generalize to all exits or settle general ignored-result diagnostics.

Current owner: [early-return recovery](expression-recovery.md#early-function-returns-and-continuing-path-types). The [shortfalls list](failure-handling-shortfalls.md) now excludes ordinary early function return from the unresolved set. Accepted records remain unreleased with unassigned targets.

## Established direction

### Audience and defaults

- The [LiteLang white paper](white-paper.md) is the foundational philosophy for LiteLang: keep ceremony low, make programs simple to read and reason about, and let people and programming agents focus on problem solving. Useful defaults and concise explicit operations should preserve strong contracts and support efficient implementation with modest runtime machinery. Native performance remains a goal requiring implementation and measurement.
- Static, strong typing, with ordinary type inference so first examples need no annotations.
- Beginner array algorithms such as sorting should use ordinary indexed comparisons and assignments rather than explicit Result handling at every read and write. The user accepts direct positional operations with typed faults and requests attached else for recovery; operation-specific and explicit whole-block scopes are selected; operation fault attribution and complete transfer/cleanup remain open; see [ordinary algorithm code](checked-fault-policy.md#ordinary-algorithm-code-must-remain-direct).
- Written library contracts must make collection requirements such as positional indexing visible in source. Requiring readers to inspect the body or an IDE is insufficient. Omitted inputs may still use deliberately inferred contracts; an explicit complete contract must not silently gain stronger requirements. Exact contract spellings remain open; see [signature visibility](collection-signature-ergonomics.md#revised-recommendation-complete-visible-annotations).
- Beginners should be able to create, pass, traverse, and write simple functions over collections before learning protocol names such as Iterable or Collection. Contextual construction and inferred requirements are candidate mechanisms, not selected generic syntax. See [collection ergonomics](collection-inference.md).
- Collection consumers depend on required behavioral capabilities, not a fixed List/Set/array provider or static extent unless the operation needs it. Compatible user/standard providers should work without forced materialization or a common boxed-object superclass. Primitive values and records must be supported through unified element-typed APIs without a mandatory primitive-wrapper collection split. Names, generic syntax, specialization/erasure, conformance, and ownership mechanisms remain open. See [consumer abstractions](collection-abstractions.md).
- Fresh nonempty bracket literals with an established element type and statically known total length infer fixed arrays [T; N], selected 2026-10-24, superseding the earlier unconditional List default. Known-size array/fixed-tuple spreads contribute their lengths. Read access is implicit; mut/var remain explicit and do not change family or extent. Growable storage requires an expected concrete type or constructor. Existing read-only providers keep their contracts. Known-type heterogeneous contributions now use normalized-union element inference. Empty [] is a valid zero-length array with its exact unknown-versus-Unit element default deferred; unresolved nonempty element and runtime-length literal provider inference remain open; see [fixed-array inference](tuple-array-shapes.md#known-size-fresh-literals-infer-fixed-arrays).
- Ordinary sequence literals preserve the user-supplied occurrence order and permit duplicates; ordered does not mean comparator-sorted or unique. A traversal-only consumer should accept compatible ordinary sets too, following their provider's order without imposing set-specific requirements. Set defaults, stronger ordering guarantees, and traversal-based positional extraction remain open. See [order and shared traversal](collection-order-and-traversal.md).
- [Immutability by default](immutability-by-default.md) is a language design goal: start with fixed bindings and read-only access; make mutation an explicit, practical capability through var/mut. Writable access adds authority, not a wider set of admissible stored values. This does not select deep freezing, purity, implicit copying, or an ownership model.
- Bindings are fixed and provide read-only access by default. Var permits binding reassignment; mut permits held-data updates. Inferred var mut x := expression grants both, with var x: mut T = expression as its annotated form.
- Operations have read access by default; affected receiver/parameter bindings explicitly carry `mut`. There is no additional function-level mutation marker.
- Minimal visibility and capability exposure by default.
- Hide derived mathematical access summaries such as A | var B | C wherever possible. Type-side var explicitly declares caller replacement; local-only var belongs inside the body. Var replaces the former slot keyword without weakening write checks; see [var access](var-access-qualifier.md) and [access ergonomics](slot-ergonomics.md).
- Explicit optional data and typed errors instead of universal nullability.
- Recoverable failures have statically typed error contracts. To obtain a fallible call's successful payload, a caller explicitly handles/inspects the outcome, supplies a default, or propagates the error. Keeping the outcome as a `Result` for later handling does not unwrap it.
- Propagation uses postfix `!` at each extracted Result step. Calls and members can continue directly, as in `load_user(id)!.load_profile()!.name`; parenthesis-heavy chains and mandatory temporary bindings are rejected as the everyday solution. `!.` consists of two ordinary postfix-chain tokens and is not nullable access. Local recovery uses an attached `else(error) { ... }` or `else { ... }` block. The error receiver is optional and introduces no implicit name when omitted. Implicit success construction does not imply automatic call-site extraction.
- Result-producing arguments need their own explicit handling/extraction before use as plain payload parameters; an outer call's else cannot handle or unwrap them collectively. Passing intact Result data remains valid when requested by the parameter. The user prefers local fallbacks in the indexed multiply example; this does not choose the remaining panic-boundary scope. See [argument recovery](recovery-boundaries.md#result-arguments-require-their-own-handling).
- One outer propagation marker must not silently extract all intermediate Result values. Stored Results remain ordinary data; no implicit member forwarding or recursive unwrapping is selected.
- Matching stored Results preserves the explicit success/failure side; the selected patterns are lowercase .ok(value) and .err(error), with tag-only .ok/.err forms available. Success construction may remain implicit without making outcome inspection implicit. Matching does not automatically unwrap, propagate, or flatten nested Results; payload patterns and later guard conditions operate only after the outcome side is identified.
- Result recovery combines success type `T` and normally completing fallback type `D` as `T | D`, collapsing identical alternatives. An explicitly exiting fallback contributes no local alternative. Conditional/match branch results and local-lambda completion payloads also have selected normalized-union inference; the full union type grammar remains open.
- A recovery handler with outward outcome `R ! E2`, handling all of `E1` from `T1 ! E1`, yields `(T1 | R) ! E2`. Partial handling retains the original unhandled error types alongside `E2`; the handler can reintroduce an error type it just consumed. Later enclosing recovery can handle those new failures. This is composition of outward outcomes at the explicit recovery boundary, with nested successful Result payloads and function/closure-targeted `!` retaining their own rules. See [fallible handler outcomes](expression-recovery.md#fallible-handler-outcomes).
- Developers can narrow success and error unions through type-pattern matching, binding an active alternative with its narrower static type. This includes unions on both sides of `!` and recovery-created unions. An intact Result preserves its outer success/failure distinction when the payload types overlap. Complete pattern grammar, overlap, and ownership rules remain open; see [union type patterns](union-patterns.md).
- Every escaping returned error must fit its established outward contract. Explicit/expected outputs cannot silently widen. LP-0012 permits eligible unannotated nonrecursive outputs to infer returned-error categories from raises, .err returns, ! forwarding, and outward fallible tails; implicit panics remain excluded.
- Returned-error propagation follows structured-exit cleanup. When postfix `!` forwards a typed error, applicable construct-level `finally` blocks in exited scopes run inner-to-outer, then the error returns from the enclosing function or closure. Cleanup preserves the pending error; it does not recover it or trigger dynamic handler search. Body-wide cleanup sections remain deferred, and no rollback or hard-abort guarantee is implied. See [returned-error cleanup](finally.md#pending-outcomes).
- Recovery for fn/if/loop/match constructs belongs inside their bodies. External error-catching else(failure) tails on whole if/loop/match constructs are rejected; operation-level call recovery remains valid. Body-wide special sections are explicitly deferred for a joint [cleanup and resource review](deferred-cleanup-and-resources.md). See [body-owned recovery](body-recovery.md).
- Panics propagate implicitly through calls without ! or Result error declarations, until an applicable handler or the unhandled-fault policy is reached. During language-managed propagation toward an outer matching handler, exited scopes run applicable `finally` blocks inner-to-outer. No-handler policy, hard aborts, and transfer implementation remain open. Cleanup-failure precedence is selected under [completion hooks](#2-completion-hooks-and-abrupt-exits); the `A & B` receiver pattern is selected separately below.

Schematic (ErrSingle,) contains one occurrence, (ErrA, ErrB, ErrC) contains several, and () means none. In written else order, independently of error occurrence order, a match consumes its match and leaves the remainder; a nonmatch runs no handler and consumes nothing. An empty remainder matches no failure clause. If the complete admitted failure and handler contracts prove exhaustion on every path, no further catch or returned-error propagation is required for those handled failures. New handler/cleanup failures and uncovered categories retain their obligations. Duplicate-occurrence consumption, diagnostic relabeling, and new-failure order remain open. See [the normative traces](expression-recovery.md#pending-occurrences-and-munching-selected).

Each individual payload has one active member; LP-0009 extends the flat outcome to retain several occurrences without a count in its type. `A & B` denotes a co-occurrence failure set: both A and B are pending, `B & A` is the same pattern, and the form is type-only (`else (: A & B)`) because it binds no value yet. Use `else (: Type)` to filter without binding or `else (name: Type)` to filter and bind; a bare `else (Type)` is a catch-all binding under the shared pattern rules. - Basic arithmetic faults use typed panics, not returned `Result` errors. Individual operation recovery uses target-level `else` with a typed filter; `!` after a typed handler explicitly propagates any remaining returned errors, while unmatched panics propagate implicitly and unwind through applicable `finally` blocks before an outer matching handler. Exact triggers, panic payloads, floating-point cases, target boundary, transfer implementation, and hard-abort policy remain open. See [arithmetic fault boundaries](arithmetic-faults.md).
- Panics should carry strongly typed categories and structured information, including underlying null access, zero division, arithmetic overflow, and related faults. This does not introduce public nullability or require every panic in a Result declaration. Exact operation policies, payloads, and host/foreign-code detection remain future work; see [typed panics](typed-panics.md).
- A user can recover from an individual operation. Returned-error handling remains explicit for `Result`; arithmetic panic recovery must be local without a prior implicit unwrap or automatic propagation, and does not require every intermediate binding to be a visible `Result`.
- Composition and interfaces as the primary reuse direction.
- Small runtime and native performance as goals, not measured achievements.

- The [T] shorthand has an accepted complete indexed-sequence direction: cheap exact count, zero-based constant-time reads, and traversal in positional order with duplicates preserved. ### Design method

- Syntax and rule decisions apply a continuity/gradient test selected 2026-10-25: a small source edit should produce a local, predictable change in meaning; similar-looking constructs should share grammar, typing, evaluation, and diagnostic shape; a semantic jump requires a visible change in the input (keyword, punctuation, type, target, channel, or explicit phase). The method is qualitative and is not mathematical differentiability or a runtime-cost promise. Learning transfer is the practical check: understanding one pattern should predict semi-similar constructs elsewhere. See [continuity and analogical coherence](continuity-and-analogy.md).

- [Independent lambda result inference](functions.md#independent-lambda-result-inference) is selected for nonrecursive local lambdas with established input types: `(n: Int) { n * 2 }` yields Int, `() { 42 }` yields Int, and `() {}` yields Unit. Require annotations for ambiguous results and retain explicit recoverable-error contracts. Unknown input/generic inference, recursive results, and public-signature policy remain separate. Conditional/match joins are selected separately. Mixed local completion payloads use the selected union rule below.
- [Mixed local result types](functions.md#mixed-local-result-types) infer a normalized plain union of completion payload types for a nonrecursive local lambda with known inputs and no explicit/expected result contract. An Int return plus a String tail infers Int | String; duplicate members disappear. Explicit/expected results still constrain every payload. Preserve composite/Result boundaries and explicit escaping-error contracts. Conditional/match result joins use the separately selected branch-result rule.
- [Conditional and match result inference](branch-result-inference.md) is selected: infer normalized plain unions of normally completing branch/arm results when no expected result contract supplies the type. Explicit/expected contracts remain constraints. Preserve no-`else` noncontributing paths, declaration defaults, genuine Unit alternatives, then T/R separation with a required final else, composite/Result boundaries, and match exhaustiveness. A multi-member union declaration initializer requires an explicit else or `?` under the separately selected rule; assignment and loop no-match paths do not. This supersedes the older prohibition on forming unions from mixed branch results.
- Union storage follows the user's clarified [metadata-plus-overlapping-payload model](union-zero.md#current-storage-model). Max-member size applies to payload capacity; full storage also includes member metadata and alignment/padding. This reconciles the C-style payload with active nominal identity and checked narrowing. Zero clears metadata and payload, but the zero-tag meaning remains open. Exact encoding/ABI and optimizations remain separate.
- [Plain-union zero membership](union-zero.md#selected-membership-of-union-zero) is selected: zero(A | B) must hold zero of exactly one listed member. Zero metadata cannot mean hidden none, an invalid tag, or multiple active members. Exhaustive A/B matching includes zero. Which member is selected remains open and must respect order-independent union identity; bytewise zeroing alone does not choose it.
- [Undirected plain-union zero construction is rejected](union-initialization-policy.md#selected-rejection-and-explicit-member-choice): x: A | B = 0 is a compile-time error when normalization leaves multiple distinct members, even if Int is listed. Do not choose a canonical/leftmost member or create an empty value. Explicit = ? and initialized compatible expressions remain available. A{}/B{} choose valid default-constructed record members; A{0}/B{0} propose whole-member zero constructors whose grammar remains open. Bare multi-member union locals also require an initializer or = ?; implicit/recursive union-zero creation still needs reconciliation with the prior broad zero rule.
- [Bare union-local declarations](union-initialization-policy.md#bare-local-declarations) are rejected when normalization leaves multiple distinct members. Require an initialized compatible expression or explicit = ?. Omission does not create zero, empty, or uninitialized readable values, and is not implicit reservation. Aliases do not bypass the rule. Existing definite-initialization and first-write rules apply to = ?. Parameter headers, fields, globals, constructor grammar, and implicit union-zero result sites remain separate.
- [Conditional union fallback](conditional-union-fallback.md) is selected: require an explicit else or `?` for a declaration initializer whose resolved T is a normalized multi-member plain union and selection can normally finish without a contributor. Exhaustive chains construct their chosen result without an initial undirected zero(T); then requires a final else and receives valid T before producing R. Keep declaration-default and branch-union inference. A wider destination alone is not the criterion. Assignment and loop no-match paths perform no write/contribution and need no union member; loop/argument/callable/aggregate zero sites remain separate.
- Callable capture/context design and environment context such as allocators are postponed at the user's request. Earlier explicit-capture directions are retained as pinned ideas rather than current language feature commitments. Existing lambda syntax and optional annotations remain in scope. See [deferred contexts](deferred-contexts.md).
- For contextual lambda headers, `()` retains the entire expected callable signature while binding none of its inputs locally. Thus `x = () { "replacement" }` can satisfy `x: fn (a: Int): String` without introducing `a` into the body. `(a)` binds the input locally; `(_)` uses the ordinary readable underscore binding with permitted nonuse. Normal input evaluation, permissions, and cleanup apply. This settles empty-header meaning within the lambda direction, not general standalone inference or complete lambda parsing; see [lambda headers](functions.md#named-underscore-and-empty-headers).
- Lambda headers may bind a positional prefix of expected inputs and omit trailing names. Under an expected `fn (left: Int, right: Int): Int`, `(left) { left * 2 }` retains both inputs and binds only the first; `(_, right)` binds the second position explicitly. Local names do not match signature names, and more header positions than expected inputs are rejected. Preserve ordinary evaluation, permissions, passing, and cleanup for every input. Destination input-label adaptation is now selected for otherwise compatible stored callables; other callable compatibility remains separate. See [partial lambda headers](functions.md#partially-named-input-headers).
- Without an expected callable type, an empty lambda header declares zero inputs: `constant := (): Int { 42 }` has `fn (): Int`. With an expected callable, retain its inputs and bind none locally. This selects independent empty-header arity; local result inference is selected separately, and compatibility/conversion of already-created callables remains open. See [independent empty headers](functions.md#empty-headers-without-an-expected-callable).
- Explicit function types use the signature without a body, as in `fn (a: Int): Int!`, whose callable result is `Int ! Error`. Function literals are ordinary value expressions usable in initializers and assignments. `var myfn: fn (a: Int): Int!;` immediately creates a zero callable; `myfn = fn (a: Int): Int! { a + 1 }` replaces it through ordinary `var` binding assignment. Broader callable compatibility, parameter-name identity, captures, ownership, and complete recursive type grammar remain open. See [function types and reassignment](functions.md#function-types-literals-and-reassignment).
- Field aggregates use record, as in `Student := record { name: String; grade: Int; }`, replacing the earlier type-body record sketch. Declared field types use colon; construction supplies predefined fields as field = expression. Named patterns use inferred braces and destinationPattern = sourceField; the previous reverse direction is superseded. field == expected compares without binding, while field: Type type-tests and binds that same-named field. Type-only testing is : Type = sourceField. Construction may name its type explicitly or omit it when a unique expected record type is known, including annotated bindings and nested record fields. Distinct identity per declaration is selected. Complete inference/brace disambiguation, generic instantiation, visibility, and memory remain open; see [records](records.md) and [aggregate clauses](aggregate-patterns.md#named-field-clauses).
- Empty contextual record initialization is selected: profile: Profile = {} constructs a record and applies its declared-default policy. Empty executable bodies, including fn () {} and _ {} match arms, still produce Unit. Expected record result types must not silently reinterpret body braces as data. The grammar must express initializer and body roles explicitly; see [initialization modes](record-initialization.md#2-two-initialization-modes).
- A simple typed declaration may omit its initializer: value: Type; immediately zero-initializes, equivalent to value: Type = 0. Var value: Type; uses the same zero initialization and exposes the writable storage contract var Type; reading still produces Type. No uninitialized state, deferred first write, or source-free destructuring is introduced. Both zero forms use a valid language-defined all-zero representation for every type and bypass declared field defaults. Function argument defaults have their separate selected rule below. See [zero initialization](zero-initialization.md).
- Explicit contextual zero initialization uses literal 0. Inferred 0 remains Int, an integer variable is not converted to a record, and nonzero integer literals are rejected for record initialization. The separate = {} form applies declared defaults. Initialization mode does not itself grant var/mut permissions.
- A zero-initialized `T ! E` contains `.ok(zero(T))`; `attempt: Int ! ReadError;` therefore starts as `.ok(0)`. Recursive zeroing preserves nested Result layers. Declaration defaults and loop value contexts use the same mapping when their type is fallible; a no-`else` conditional is noncontributing, not a zero result. Representation and ABI remain open; see [Result zero](zero-initialization.md#result-and-error-boundaries).
- A zero-initialized function performs no user-body work and returns zero of its declared result type, including `.ok(zero(T))` for a `T ! E` result. Callee and argument evaluation retain their ordinary order and effects; required argument ownership/cleanup still applies. The zero callable does not update data through `mut` or `var` grants. Callable type grammar, complete ownership/cleanup timing, representation, and ABI remain open; see [zero-initialized functions](zero-initialization.md#zero-initialized-functions).
- Ordinary user implementation argument omission requires public permission and an applicable explicitly declared default. The selected zero implementation needs no actual default definition or execution for publicly omittable ordinary inputs. This supersedes automatic zero argument defaults, including Int and Unit. Supplied arguments take precedence. Unused/unnamed inputs and zero callables retain their input contracts. Default timing is selected separately; complete grammar and permission-aware typing/dependencies, general lexical lookup/captures, complete omission-marker integration, complete recursive named-call grammar, and caller-access permission integration remain open; core named-call routing and validation are selected separately; see [argument defaults](union-parameter-defaults.md) and [functions](functions.md#omitted-value-arguments).
- The four-form direction is selected: value: Type; means implicit zero, = 0 means explicit zero, = {} means declared defaults, and = ? explicitly requests uninitialized storage. The final form is a special construction/storage marker for simple typed value declarations, not a usable unknown value. Full initialization-state, first-write, eligible-layout, and allocation/cleanup contracts remain open. Reserve(), {?}, ?=, and ?Type are unselected alternative spellings, not synonyms. See [reserved storage](reserved-storage.md).
- Whole-value first initialization of an explicitly reserved binding uses = without var, once per execution path. Multiple source sites in mutually exclusive branches are allowed; every path reaching ordinary value use must have initialized the binding. Missing branches are compile errors, not implicit zero/default construction. Later whole-binding replacement requires var. The first successful write installs the valid value; before it, both fixed and var reserved storage reject ordinary reads. After it, fixed storage is readable without replacement permission, while var storage remains readable/writable. The same state checks apply alongside union read-flow rules without adding Unit or an unknown member. Partial/callee construction and cleanup remain open. See [first initialization](first-initialization.md#writable-before-initialization-readable-afterward).
- Large arrays/buffers are the main motivation for explicit uninitialized reservation. Storage exists; payload bytes are unspecified, not null/missing storage or readable random values. Avoid a mandatory preliminary zero pass before bulk filling. Element-initialization syntax, coverage/prefix tracking, allocation policy, and partial cleanup remain open; see [reserved arrays](reserved-storage.md#main-use-case-large-arrays-and-buffers).
- Initialization requirements describe source semantics, not mandatory physical stores. In var x: User; x = make_user();, the optimizer may omit unobservable zero stores and use untouched destination storage internally while preserving all defined observations and required cleanup, including exits before replacement. Every type has a valid all-zero representation regardless of optimization; this does not expose a source-level uninitialized value. See [semantic initialization versus physical writes](memory-and-performance.md#semantic-initialization-versus-physical-writes).
- Each record type declaration creates a distinct type, including unnamed inline declarations, even when field shapes are identical. Convert through explicit destination reconstruction, subject to visibility and ownership. Contextual construction and headless deconstruction do not introduce implicit structural assignment. Reuse one shared record type declaration when different fields need the same type; see [record type identity](record-type-identity.md).
- Named transparent aliases use Alias := type TypeExpression for both simple and composite types. The keyword covers the whole right-hand type expression, introduces no nominal wrapper, and is not optional in alias definitions. Ordinary value bindings remain unchanged; name capitalization never chooses their kind. See [type aliases](type-aliases.md).
- Plain unions ignore member order, flatten nested plain unions, and remove duplicate resolved type identities, including transparent aliases. A | (B | A) is the same type as A | B. Distinct record declarations and enum cases retain identity; Option/Result and whole product alternatives are not flattened or redistributed. Match-arm order remains source order. See [union normalization](union-normalization.md).
- An existing value of a listed member type is admitted to a plain union automatically, without a cast or explicit case wrapper. Using an arbitrary union value as a particular member requires checked narrowing. Resolve aliases/normalization before exact membership; do not infer numeric conversions, equal-shaped record conversion, or interface implementation. See [union membership](union-membership.md).
- A plain union widens automatically to another when every normalized source alternative is an exact destination member. Preserve the active member's identity; no numeric conversion, record reconstruction, interface conversion, or recursive container/Result conversion follows. Reverse assignment needs checked narrowing when the source permits uncovered alternatives. Ownership, permissions, and layout remain separate; see [union widening](union-widening.md).
- The [reference comparison](union-membership-comparison.md) distinguishes direct unions (Scala/TypeScript), discriminated sums (Odin/V), explicit named cases (Rust/Zig/Swift), common-root sealed hierarchies (Kotlin/Dart), C++ variant construction, and Python/Lua dynamic behavior. It supports the chosen admission ergonomics without importing their nullable defaults, casts, hierarchy obligations, or representation policies.
- Early returns are encouraged.
- Common field reads through a plain union require a readable field on every possible alternative. The result is the normalized union of field types, including duplicate removal and order independence. Missing or inaccessible fields reject the projection; they are not bottom-type members to discard during normalization. Record identity stays nominal. Methods and full flow/ownership rules remain separate; see [union field reads](union-field-reads.md).
- Field writes through a plain union must be accepted by every possible target field, with mut and writable access. For P.field: C | D and Q.field: C | E, reading through P | Q produces C | D | E but only C can be written without narrowing. A standalone variable declared C | D | E can accept any member; the projected read type does not replace each parent's storage contract. See [union field writes](union-field-writes.md). Explicitly presentable access contracts are investigated in [union values and access](union-values-and-access.md); their public notation and first-class status remain proposals.
- Ordinary `Result` success is implicit when an appropriate contract is expected; errors are explicit.
- A var-qualified function parameter provides temporary access to the caller's location. Assignment through it replaces the supplied caller variable or field. The explicit call grant replace(var value) requires an already writable location; a whole binding must be var. Var alone grants no held-data mutation. This selects neither public pointers/general reference values nor a complete borrowing model. Ordinary read-only value transfers use the general copy default with no implicit references; type-specific eligibility, general aliasing, and full access compatibility remain deferred; see [var parameters](slot-parameters.md).
- Type-side var is the canonical replacement qualifier, superseding slot in signatures, explicit call grants, and access summaries. Fn(param: var T) receives writable caller storage; local-only fn (var param: T) headers are omitted. Use var param := param in the body for local working state. The shorthand fn (param: var) requires an inferable value type; general parameter inference remains open. See [var access](var-access-qualifier.md).
- A mut-qualified parameter requires an explicit mut argument grant, as in rename(mut userVar). The caller must already possess mutable access, and writes affect that supplied data rather than a silent detached copy. Ordinary read-only inputs grant neither writable caller-data access nor caller replacement. See [caller grants](caller-mutation-grants.md).
- Local-only var parameter headers are retired: use local declarations and sequential shadowing inside a normal parameter's body. Var count := count preserves the input as the working value; var count := 5 initializes that working value to 5.
- Within an access contract, var marks accepted replacement alternatives: A | var B | C reads A/B/C and accepts B on a permitted write. It supersedes mut for this marker; declaration var/mut keep their separate meanings. Grouped scope distributes within one contract: var (A | B) is equivalent to var A | var B. A var binding of A | B has that whole-binding replacement summary, independently of mut. Prefix scope preserves the full denotation of a transparent alias operand. Full access declaration grammar, contract boundaries, and first-class access types remain open. See [var access qualifier](slot-access-qualifier.md).
- Fallible type notation is `T ! E`; `T!` means exactly `T ! Error`, declaring the general recoverable error contract. A plain `T` declares no recoverable failure. Refined error types remain available; `!T` is not an alternate spelling. Type and expression contexts distinguish a fallible type from postfix propagation without whitespace semantics.
- In type declarations, union `|` binds more tightly than binary fallible type `!`: `A|B|C!D|E|F` is valid and means `(A | B | C) ! (D | E | F)`. Official reference documentation prefers the explicitly grouped form for union operands on either side; this is a style preference, not a restriction on users' code. Precedence with other constructors and associativity of repeated `!` remain open. See [type grouping](fallible-types-and-error-composition.md#grouping).
- Multiline strings and adjacent literal joining are desired.

### Operators

- Use `and`, `or`, and `not`.
- Use `==` for equality and `=!=` for its Boolean complement; prefix not remains available and negates an entire comparison chain.
- Comparison binds more tightly than `not`, followed by `and` and `or`.
- All ten operators ==, =!=, >, >!, <, <!, >=, >!=, <=, and <!= form comparison chains at exactly one shared precedence level, checking adjacent operands with strict Bool results. Negative forms complement their corresponding positive comparison for one adjacent pair.
- Chain operands evaluate at most once from left to right; a false comparison skips later operands and comparisons. All pairs must type-check.
- Mixed comparisons and changes in direction use the same adjacent-pair rule; `not` applies to the complete chain unless parentheses specify another grouping.
- Ordinary operator operands evaluate left to right after grouping. Calls evaluate the callee first, then supplied argument expressions in source order, then invoke the callable. Short-circuiting skips unneeded expressions.
- Assignment selects its target once before the right-hand side; compound updates read its current value before their right operand, then compute and write the result. Alias and lifetime rules still need formalization.
- `?=` and `!=` have no selected meaning in the current design.
- [Negated comparisons](negated-comparison-operators.md) are selected, 2026-10-23: =!= negates ==, >! negates >, >!= negates >=, <! negates <, and <!= negates <=. Each underlying comparison executes once if reached; complement its normal Bool result while preserving effects/failures. All ten share exactly one comparison precedence and the existing adjacent-pair chain rules. Recognize longer comparison tokens before their prefixes in expression context; trailing = is part of the comparison, not an update. Preserve the selected attached T! type boundary: x: Box<Int>! = load(), x: Box<Int>!= load(), and x: Box<Int>!=load() are equivalent, while x: Box<Int> != load() is invalid shorthand. Angle-bracket generic source syntax remains unselected, but any adoption must preserve the conditional type-context split. Unicode operators and infix not phrases are not selected. All ten nonbinding comparison-pattern prefixes are also selected, with ordinary meanings and runtime RHS evaluation once when reached. Full generic grammar, complete pattern operands, custom comparison/Float contracts, and executable verification remain separate.
- Supported `op=` updates use defined underlying operations and evaluate the target once.
- [Contextual division](division.md#floating-calculation-and-integer-storage), clarified 2026-10-25: floating operands supply floating arithmetic, including nonintegral literals and established values. Int storage accepts the quotient using / truncation toward zero or _/ floor: 7.5 / 2 stores 3, -7.5 / 2 stores -3, -7.5 _/ 2 stores -4, and 2 / 0.5 stores 4. Never truncate operands before division. Float/Double destinations retain fractional /, including 2 / 7; integer-only division without floating evidence/expectation retains its integer default.
- The earlier operand-only / rule is superseded, and result-directed wording is clarified: Int storage does not force integer arithmetic when a floating operand is present. This division rule does not select a general Float-to-Int assignment cast, mixed floating-width precision, out-of-range/non-finite storage behavior, or complete expected-type propagation through unresolved subexpressions/calls/returns. The user separately selected preservation of floating intermediates until the complete admitted expression reaches Int storage: (7.5 / 2) * 2.0 stores 7; half: Int = 7.5 / 2 stores 3 before half * 2 produces 6. Parentheses only group. Explicit rounding operations retain their own boundaries; see [the selected rule](division.md#floating-intermediates-and-storage-boundaries). Ordinary integer-only division still needs no floating intermediate or mandatory named helper.
- [Arithmetic family / _/ % _%](division.md#integer-remainder-and-modulo-selected), selected 2026-10-25: / with an Int quotient and % are the truncating integer pair; _/ and _% are the floor pair. A nonzero remainder follows the dividend, while a nonzero modulo follows the divisor. The integer identities are a == b * (a / b) + (a % b) and a == b * (a _/ b) + (a _% b). Updates are /=, _/=, %=, and _%=; the operators share multiplicative precedence/left association. The earlier always-fractional / and // / %% floor spellings are superseded. Ordinary methods are requested in addition, including plus, div, and floorDiv, with working rem/mod names. Exact signatures/dispatch, mixed operands, conversions, and faults remain open. The user retains compact/spaced equivalence, with underscore/identifier scanning unresolved; no mandatory-space rule or // comment rule is selected. See [the selected family](arithmetic-methods-and-division-revision.md).
- Retiring `//` arithmetic does not select line comments. Once an operator boundary is established, recognize the longer updates `/=`, `_/=`, `%=`, and `_%=` before their shorter prefixes; compact underscore/identifier boundaries remain unresolved.

### Conditional and loop direction

- One `if` form works for actions and values; branch braces establish ownership.
- One `loop` keyword handles Boolean, iterable, and unconditional sources.
- The loop header shape is source-capability-neutral: `loop source as item { ... }` keeps the same item binding, body, `then`, and `.item`/`.value` rules across sources. `.index` is a positional capability, available for arrays/lists/slices and explicit reverse positional views, not for a unique set or other nonpositional iterable. A set traversal does not synthesize an index or stable positional order; requiring a position needs an explicitly ordered source or an external counter. Reverse traversal is an explicit source/provider capability, not a silent loop mode. See [continuity examples](continuity-and-analogy.md#similar-input-different-capabilities).
- Remove post-condition loop syntax; use inner conditions and explicit exits.
- Loop headers allow one optional item identifier introduced by as; colon and header patterns are retired. Count/value receiver lists, receiver-slot shadowing, and header tuple patterns are retired. The item name denotes the same current element as .item; destructuring and refutable selection belong inside the body. See [item naming](loop-receivers.md).
- Loop metadata supplies .item, .count, and .value for every source. `.index` is additionally available only for positional sources such as arrays, lists, and slices; a unique set or other nonpositional iterable exposes `.item` but not `.index`. Index is zero-based traversal position, independent of original source keys/positions and reversal/step. Count counts entered iterations. Item and positional index are readable during active iterations and as last-visited metadata in then if an iteration occurred, not in source/condition evaluation. After zero entries, then exposes a typed zero `.item` and, for positional sources, `.index == 0`, with .count == 0 distinguishing them from an actual first entry. Count/value are available before the first condition, in the body, and in then. Retain last-item state for completion only when observable use requires it.
- Loop .value replaces .acc and automatic Option accumulators. It has a static body-result type and is zero-initialized before iteration; tail completion, continue value, or break value commits; plain continue and bare break preserve. No value_or helper or previous receiver is required. See [loop value](loop-value.md).
- Do not inject implicit ordinary names such as `it` or `acc`.
- Direction and stepping should be source/range capabilities rather than more loop keywords.
- Plain continue preserves .value and advances; continue value commits early and advances. `continue @tag [value]` applies the same rule to an explicitly named enclosing loop: it commits to that loop before advancing when a value is supplied, and preserves `.value` without one. Bare break preserves .value and runs then. Break value commits its T operand, stops the nearest loop, and runs then. `break @tag [value]` applies the same loop exit to an explicitly named enclosing loop; without a payload it preserves `.value`, and with one it commits T. Untagged break still targets the nearest loop even if it has a tag. A tagged return supplies T to its named target and runs that target's then if present; constructs exited on the way skip their own then blocks. Target support is sparse: break/continue target loops; tagged return targets loops, ifs, or general result blocks; plain return targets the nearest function/closure. Functions and closures are not current tagged-return targets; function tags, nested-function/lambda boundary crossing, and any visibility or metadata role remain deferred. Unsupported operation–target pairs are invalid.
- Exit target and payload boundaries, selected 2026-10-25: after `return`, `break`, or `continue`, an optional target is exactly one `@` identifier, and the payload begins at the next token. A target followed directly by `.` is rejected as ambiguous; `@scan.value` is not a target-plus-payload spelling. Write `@scan (.value)` for a targeted current-context metadata payload, or `(@scan.value)` for an untagged payload. A context-reference payload may be repeated explicitly after the target, as in `return @outer @inner.value`, which is unambiguous. Whitespace and comments never choose the reading. An untagged `continue .value` remains valid.
- Loop completion uses receiverless then { ... }. Its current context is the owning loop, tagged or untagged: .count and .value are available directly. The tail expression supplies the completion result, including Unit; the earlier completion-receiver and action-preservation distinction is superseded. Nested contexts retain no outward field search.
- Without then, normal completion returns final .value; with then it returns that block's tail expression, and then {} returns Unit.
- Loop type inference uses body constraints and destination-side expected types. A Long destination can constrain .value, including a body consisting only of .value. With then, expected final type R constrains body type T only through actual type relationships. Numeric promotion/casts remain the arithmetic contract; see [loop inference](loop-type-inference.md).
- Concise optional search loops should not require redundant `None` bodies or `else { None }`.

### Tags

- A tag is an explicit typed construct context, not a global loop object.
- Put it before the construct: `@name loop ...`, `@name if ...`, or `@name { ... }`.
- Construct kind determines metadata and permitted operations.
- Tags follow lexical shadowing; an inner tag may reuse a name.
- Loop `.field` shorthand refers only to its current loop context, with no outward fallback; within a conditional, use an explicit loop tag. Conditional `.value` requires `@tag.value` and is available only inside the conditional's attached `then`; ambiguous leading-dot metadata reads are rejected.
- `@name.field` explicitly selects a named context.
- A loop's tag remains accessible in its attached completion block. Final count and typed value are readable there; other metadata must be valid for that phase. This scope does not keep iteration-local items/references alive automatically. See [completion tag access](unified-loop-completion.md#access-through-the-owning-loop-tag).
- `return @tag [value]` exits a named construct; its payload supplies the target's pre-then T, and the target's `then` runs to produce R if present. Constructs exited on the way skip their `then` blocks. Without a target `then`, T is the target result; an omitted payload is `Unit`.

## Contracts to settle next

### 1. Loop contribution and construct-result inference

Define body-result type T and final construct-result type R independently. The .value storage has T and is zero-initialized; it is not automatically Option<T>. A body whose only value-producing path is `.value` is circular and remains ambiguous without an independent type constraint; the no-contributor `Unit` default does not resolve it. Complete inference for last-value loops, Unit actions, targeted-result-only search loops, and optional results without nested wrapping. Implement a coherent inference specification for the selected no-then .value rule and any future nonzero initialization mechanism.

When a loop has no contributing path and nothing else constrains T, T defaults to Unit; an expected type can override that default. Plain continue and bare break do not themselves contribute Unit; an action body that normally completes with Unit does. A `then` result independent of `.value` determines R but leaves T at its default. See [noncontributing loop paths](loop-type-inference.md#loops-with-no-contributing-path).

For conditionals, when no normally completing branch constrains T, T defaults to Unit; an expected type can override it. A no-`else` conditional is partial: no match is noncontributing. A declaration keeps its default (`zero(T)` or reserved with `?`), an assignment performs no write, a loop body contributes nothing, and a value-required context requires `else`; `then` requires `else`. This differs from a normally completing `Unit` contribution, which the loop does commit. Inside the `if`, use an explicit loop tag to read the enclosing loop's `.value`.

### 2. Completion hooks and abrupt exits

For a typed panic that matches a handler in the same scope as its `finally`, the handler recovers first and that scope's `finally` runs once as it exits. If the panic escapes toward an outer matching handler, exited inner scopes run their applicable `finally` blocks first.

The single receiverless `then` is selected for loops and complete conditional chains. A conditional `then` requires a final `else`, processes the selected T into final R, and exposes read-only `@tag.value` only in that block. A partial no-`else` conditional cannot carry `then`. `then` names result processing; reserve `finally` for cleanup that preserves a pending result or exit. When both hooks are attached to a loop or conditional, `then` completes before `finally` runs cleanup as the construct exits. Normal completion and a return targeting the conditional supply T and run its `then`; a return to an outer target skips the inner conditional's `then`, while applicable cleanup still runs on exit. Propagated errors and unhandled panics provide no conditional T and skip result processing; applicable cleanup runs while leaving. During language-managed panic propagation, exited-scope `finally` blocks run before an outer matching handler. Exact attachment syntax/scope remains open. Loop count and typed value remain available from the owning context.

The user selected cleanup-only `finally`: no implicit pending-outcome receiver, recovery, or result/exit transformation. If cleanup completes normally, preserve the pending result, control-flow exit, propagated recoverable error, or typed panic. On normal loop/conditional completion with both hooks, `then` completes before `finally`; the cleanup result does not replace the construct result. If any failure is pending, preserve it as primary and retain every cleanup failure as secondary. If only normal completion is pending, the first cleanup failure becomes primary and cancels that completion. A same-scope handler recovers a matching typed panic before that scope's `finally` runs once on exit, so a later cleanup failure is primary. The `A & B` receiver pattern is selected; still define the `&` form's public value/operations, which scopes can attach `finally`, and no-handler/hard-abort behavior. A reusable failure-aggregation type or mechanism for other multi-failure cases is a separate open design question; see [failure aggregation](finally.md#failure-aggregation-and-open-design).

The selected policy prevents a cleanup failure from hiding the failure that caused cleanup to run. For example, when writing fails with `DiskFull` and closing then fails with `CloseFailed`, callers must still see `DiskFull` as the primary failure and retain `CloseFailed` as secondary. No public aggregate type, collection shape, or inspection API is selected; `A & B` is the selected order-insensitive co-occurrence pattern, and the `&` form binds no value. A general `Error` accumulator could serve other aggregation cases, but a recoverable-error-only type must not erase the separate typed-panic channel; any shared carrier must preserve each component's category and match behavior. The user selected declaration-ordered member-wise handling: each typed handler consumes matching pending members, and the next clause sees the remainder. Clause order is observable: individual `:A` and `:B` filters both run when both members are pending, while a combined `A & B` clause consumes both and prevents later individual consumers. A surviving remainder propagates. The `&` form's public value/operations and duplicate-member consumption remain open.

Recovery chains compose as nested expressions: each later `else` wraps the entire preceding recovery, including its handler body, and can catch a matching new failure from that handler. A handler remains outside its own recovery boundary. Separate assignments show the Result type progression but cannot retroactively catch a panic from an earlier statement; chained outer recovery is active during inner evaluation. Explicit Result extraction and function/closure-targeted `!` retain their existing rules. A new handler failure joins the already pending remainder: consuming A from an A-and-B failure set and then failing with C leaves B and C pending, with A still consumed. A subsequent B handler can consume B, but its recovery value cannot make the expression successful while C remains. The known occurrence order preserves the older B before the handler's new C under LP-0007. The `&` form's public value/operations and repeated-type combined-pattern matching remain open; see [fallible handler outcomes](expression-recovery.md#fallible-handler-outcomes).

Break value is selected as commit-and-stop followed by normal completion. Tagged-return behavior is selected: its payload satisfies T and the named target's `then` produces R when present; intermediate `then` hooks are skipped. Labeled continue is selected: an optional value commits to the named loop before it advances; intervening constructs skip their `then` blocks.

### 8. Typed recovery syntax and arithmetic failure boundaries

## Superseded suggestions

- Combined whole-value-plus-nested collectors, including the proposed name: (subpatterns) and name @ pattern spellings. Use a variable collector for the whole supplied component or a pattern collector for its contents; colon retains its type role. This rejection does not remove ordinary nested tuple destructuring.

- Keeping slot as a separate source keyword for caller replacement. Type-side var now carries the same contract, and explicit var call grants preserve visibility. The earlier rejected left-side fn (var param: T) substitution and local-only header proposal do not define this later type-side form.

- Typed mutation prefixes before names, including mut user: User and fn (mut user: User). Use user: mut User in annotated declarations/parameters; inferred mut user := expression remains valid.

- Bare None as an absent-case pattern or a special prelude-constructor exception. Use `.None`; bare pattern identifiers bind.
- Bare `User` as a type-only arm selected through type-name lookup. Use the selected marked `: User` type-only pattern instead.

- Indentation or newlines as statement/body delimiters.
- Optional unblocked function, conditional, and loop bodies.
- The earlier pattern-and match-arm separator. Use pattern if guard; and remains between subsequent guard operands. The alternative as-name arm marker was considered but not selected.
- Provisional LiteScript `if let` headers or mandatory `case`, `=>`, or `then` separators in match arms.
- `do/end`, `then/endif`, or specialized `endfn/endloop` as the selected block system.
- Mandatory parentheses around every conditional as the chosen source/body divider.
- Post-tested loop syntax and a separate required `loop if` spelling.
- Treating every loop receiver as an automatic metadata tuple.
- Changing the supplied value based on whether a pattern is a simple name or tuple.
- Requiring `.with_state()` or a separate `with` clause just to access ordinary loop metadata.
- Implicit `it`, global `loop.field`, or a current-context lookup that searches outward.
- A prohibition on nested tag shadowing.
- Suffix tags or `name: construct` as the current tag placement.
- Mandatory `Ok(...)` on normal success paths.
- Automatic extraction of success and propagation of recoverable failure from an ordinary call without an explicit caller choice.
- Prefix `try` or postfix `?` as recoverable-error propagation aliases; postfix `!` is selected.
- Requiring a `?` marker to retain a call's Result outcome.
- Silently inferring additional escaping recoverable errors outside a function's declared error contract.
- Requiring every fallible declaration to use general Error instead of allowing refined error contracts. `T!` deliberately chooses general Error; `T ! E` retains a refined contract.
- Mandatory trailing `None` or redundant empty clauses for simple searches.
- Semicolons suppressing final-expression results.
- Requiring a semicolon after a complete block item, or the earlier prohibition on allowing one. Trailing semicolons are now optional and allowed.
- Continuing an unparenthesized block value across its item boundary through an operator, call, member access, or indexing.
- Treating `_` as a nonbinding wildcard or prohibiting reads of it. It is an ordinary underscore-prefixed name; ordered shadowing replaces the intermediate wildcard decision.
- Requiring unique binding names within a single pattern or prohibiting sequential local shadowing in the same block. Later pattern names and later local declarations shadow earlier ones; parameter/field/module declaration lists retain separate rules.
- `_ = value` as special discard syntax. It is ordinary assignment requiring an existing var binding with a compatible type.
- Granting writable owned fields through `var` alone; `mut` is required explicitly.
- Requiring an additional function-level mutation marker beyond explicit `mut` receiver/parameter contracts.
- Rejecting comparison chains merely to simplify the grammar, or treating them as ordinary left-associated binary comparisons.
- Requiring verbose named division helpers as the only ordinary integer interface; / and _/ provide the selected truncating and floor operations, with named methods requested in addition.
- Earlier always-fractional / and operand-only / rules, // floor division, and %% modulo spellings. The final selected family is /, _/, %, and _%; tilde and R-style alternatives were not chosen.
- `?=` equality or conventional `!=` inequality as currently selected operators.
