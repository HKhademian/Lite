# Decisions and open questions

Snapshot: **2026-10-20**. Source: the language-design discussion in this chat. No compiler implementation or conformance result is implied.

## Established direction

### Audience and defaults

- Static, strong typing, with ordinary type inference so first examples need no annotations.
- Beginner array algorithms such as sorting should use ordinary indexed comparisons and assignments rather than explicit Result handling at every read and write. The user accepts direct positional operations with typed faults and requests attached else for recovery; full capture scope and transfer/cleanup remain open; see [ordinary algorithm code](checked-fault-policy.md#ordinary-algorithm-code-must-remain-direct).
- Written library contracts must make collection requirements such as positional indexing visible in source. Requiring readers to inspect the body or an IDE is insufficient. Omitted inputs may still use deliberately inferred contracts; an explicit complete contract must not silently gain stronger requirements. Exact contract spellings remain open; see [signature visibility](collection-signature-ergonomics.md#revised-recommendation-complete-visible-annotations).
- Beginners should be able to create, pass, traverse, and write simple functions over collections before learning protocol names such as Iterable or Collection. Contextual construction and inferred requirements are candidate mechanisms, not selected generic syntax. See [collection ergonomics](collection-inference.md).
- Collection consumers depend on required behavioral capabilities, not a fixed List/Set/array provider or static extent unless the operation needs it. Compatible user/standard providers should work without forced materialization or a common boxed-object superclass. Primitive values and records must be supported through unified element-typed APIs without a mandatory primitive-wrapper collection split. Names, generic syntax, specialization/erasure, conformance, and ownership mechanisms remain open. See [consumer abstractions](collection-abstractions.md).
- A bracket literal without a more specific expected sequence type defaults to growable List: numbers := [1, 2, 3] infers `List<Int>`. Var/mut changes permissions, not collection family; growth still requires mutable access. An explicit expected array type may select fixed layout under its eventual construction contract. Empty/heterogeneous literal inference, complete collection type syntax, owner representation, and copy/lifetime rules remain open. See [lists](lists.md) and [sequence storage families](sequence-types.md).
- Ordinary sequence literals preserve the user-supplied occurrence order and permit duplicates; ordered does not mean comparator-sorted or unique. A traversal-only consumer should accept compatible ordinary sets too, following their provider's order without imposing set-specific requirements. Set defaults, stronger ordering guarantees, and traversal-based positional extraction remain open. See [order and shared traversal](collection-order-and-traversal.md).
- [Immutability by default](immutability-by-default.md) is a language design goal: start with fixed bindings and read-only access; make mutation an explicit, practical capability through var/mut. Writable access adds authority, not a wider set of admissible stored values. This does not select deep freezing, purity, implicit copying, or an ownership model.
- Bindings are fixed and provide read-only access by default. Var permits binding reassignment; mut permits held-data updates. Inferred var mut x := expression grants both, with var x: mut T = expression as its annotated form.
- Operations have read access by default; affected receiver/parameter bindings explicitly carry `mut`. There is no additional function-level mutation marker.
- Minimal visibility and capability exposure by default.
- Hide derived mathematical access summaries such as A | var B | C wherever possible. Type-side var explicitly declares caller replacement; local-only var belongs inside the body. Var replaces the former slot keyword without weakening write checks; see [var access](var-access-qualifier.md) and [access ergonomics](slot-ergonomics.md).
- Explicit optional data and typed errors instead of universal nullability.
- Recoverable failures have statically typed error contracts. To obtain a fallible call's successful payload, a caller explicitly handles/inspects the outcome, supplies a default, or propagates the error. Keeping the outcome as a `Result` for later handling does not unwrap it.
- Propagation uses postfix `!` at each extracted Result step. Calls and members can continue directly, as in `load_user(id)!.load_profile()!.name`; parenthesis-heavy chains and mandatory temporary bindings are rejected as the everyday solution. `!.` consists of two ordinary postfix-chain tokens and is not nullable access. Local recovery uses an attached `else(error) { ... }` or `else { ... }` block. The error receiver is optional and introduces no implicit name when omitted. Implicit success construction does not imply automatic call-site extraction.
- Result-producing arguments need their own explicit handling/extraction before use as plain payload parameters; an outer call's else cannot handle or unwrap them collectively. Passing intact Result data remains valid when requested by the parameter. The user prefers local fallbacks in the indexed multiply example; this does not choose the remaining panic-boundary scope. See [argument recovery](recovery-boundaries.md#result-arguments-require-their-own-handling).
- One outer propagation marker must not silently extract all intermediate Result values. Stored Results remain ordinary data; no implicit member forwarding or recursive unwrapping is selected.
- Matching stored Results preserves the explicit success/failure side; the selected patterns are lowercase .ok(value) and .err(error), with tag-only .ok/.err forms available. Success construction may remain implicit without making outcome inspection implicit. Matching does not automatically unwrap, propagate, or flatten nested Results; payload patterns and later and conditions operate only after the outcome side is identified.
- Result recovery combines success type `T` and normally completing fallback type `D` as `T | D`, collapsing identical alternatives. An explicitly exiting fallback contributes no local alternative. This does not establish automatic union inference for other constructs or the full union type grammar.
- Developers can narrow success and error unions through type-pattern matching, binding an active alternative with its narrower static type. This includes unions on both sides of `!` and recovery-created unions. An intact Result preserves its outer success/failure distinction when the payload types overlap. Complete pattern grammar, overlap, and ownership rules remain open; see [union type patterns](union-patterns.md).
- Every recoverable error that can escape must be covered by the function's explicitly declared error contract, whether explicitly returned or forwarded by `!`. Inference must not silently widen the declared contract.
- Recovery for fn/if/loop/match constructs belongs inside their bodies. External error-catching else(failure) tails on whole if/loop/match constructs are rejected; operation-level call recovery remains valid. Body-wide special sections are explicitly deferred for a joint [cleanup and resource review](deferred-cleanup-and-resources.md). See [body-owned recovery](body-recovery.md).
- Panics propagate implicitly through calls without ! or Result error declarations, until an applicable handler or the unhandled-fault policy is reached. During language-managed propagation toward an outer matching handler, exited scopes run applicable `finally` blocks inner-to-outer. No-handler policy, hard aborts, and transfer implementation remain open. Cleanup-failure precedence is selected under [completion hooks](#2-completion-hooks-and-abrupt-exits); the aggregate carrier remains open.
- Panics use a separate path; postfix ! does not catch them. The same target-level else surface handles typed panics and Result errors. Untyped handlers match all supported failures; typed receiver patterns handle only the matching type. Unmatched panics propagate implicitly; unmatched returned errors require explicit handling or `!`. Exact capture boundary, broad mixed-channel receiver typing, transfer implementation, and no-handler policy remain open. See [shared expression recovery](expression-recovery.md). Postfix `!` is propagation, not a panic-producing assertion.
- Basic arithmetic faults use typed panics, not returned `Result` errors. Individual operation recovery uses target-level `else` with a typed filter; `!` after a typed handler explicitly propagates any remaining returned errors, while unmatched panics propagate implicitly and unwind through applicable `finally` blocks before an outer matching handler. Exact triggers, panic payloads, floating-point cases, target boundary, transfer implementation, and hard-abort policy remain open. See [arithmetic fault boundaries](arithmetic-faults.md).
- Panics should carry strongly typed categories and structured information, including underlying null access, zero division, arithmetic overflow, and related faults. This does not introduce public nullability or require every panic in a Result declaration. Exact operation policies, payloads, and host/foreign-code detection remain future work; see [typed panics](typed-panics.md).
- A user can recover from an individual operation. Returned-error handling remains explicit for `Result`; arithmetic panic recovery must be local without a prior implicit unwrap or automatic propagation, and does not require every intermediate binding to be a visible `Result`.
- Composition and interfaces as the primary reuse direction.
- Small runtime and native performance as goals, not measured achievements.

- The [T] shorthand has an accepted complete indexed-sequence direction: cheap exact count, zero-based constant-time reads, and traversal in positional order with duplicates preserved. Mut access adds supported element replacement. Underlying hooks are get_index, set_index, and iterable; general keyed Indexable need not supply the full sequence bundle. Growth, ownership, contiguous storage, full generic/protocol grammar, and stored representations are separate. See [indexed sequences](indexed-sequence-contract.md).

### Syntax and results

- Braces are required for bodies.
- Complete record constructions end outer declaration/assignment/exit items without requiring semicolons, including record field declarations with such defaults. Trailing semicolons remain allowed; inner initializer fields still need commas. The requested x := { a = 1, b = 2 } inferred form needs brace disambiguation and identity rules; see [record literal boundaries](record-literal-boundaries.md).
- Existing-name type tests use `if person: User { ... }` without redeclaration. Narrowing changes static knowledge, not the value or declared type; mutation stability, logical composition, negative/early-return flow, and generic/subtype semantics remain to formalize. See [type tests and narrowing](type-tests-and-narrowing.md).
- Conditional patterns reuse declarations: `if Some(value) := expression` and `if value: Type = expression`. Matching binds branch-local names and permits lexical shadowing; no `let` keyword is added.
- Every conditional owns a result context, optionally named with `@tag`. Its result starts at zero; when an `if`/`else if` chain has no final `else` and no condition matches, that zero is the normal result. When no normally completing branch constrains its type, it defaults to `Unit`, overridable by an expected type. The selected conditional `then` follows the complete chain, receives the branch/zero result `T`, and produces final type `R`. Read-only `@tag.value` is available only inside that attached `then`; conditional contexts do not participate in leading-dot lookup, and ambiguous leading-dot metadata access is rejected rather than searched outward. Conditional condition metadata is hidden; if branch identity is needed after selection, include it in `T`. See [conditionals](conditionals.md) and [tags](tags-and-contexts.md).
- Pattern matches and Boolean guards combine through and, as in `if Some(user) := find_user(id) and user.age > 14`. Operands run left to right and stop at the first mismatch/false result; bindings from successful patterns are available to later operands and the successful body, not else or following code. Binding-producing or/not and repeated chain names remain open; see [conditional pattern chains](condition-chains.md).
- Match arms may extend their initial pattern through and with Boolean conditions and additional explicit pattern matches. Earlier bindings are available to later operands and the body; false/mismatch tries later arms, and the first fully successful arm is selected without implicit fallthrough. Nested typed destructuring uses the same pattern system. See [match arm chains](match-guards.md).
- Match arms use pattern { body } without case, an arrow, or required arm separators; trailing semicolons after arm bodies are allowed. Match shares action/value syntax and requires exhaustive coverage for every match. Ignored cases need an explicit arm, such as _ {}, whose empty block already returns Unit. Complete coverage proofs, optional else fallback syntax, and ownership remain open; see [match coverage](match-coverage.md).
- Enum case shorthand keeps its dot: `.started` or `.completed`, with the owner inferred from a single established match-subject or expected enum type. Payload cases use the same form, such as `.Click(x, y)`. Qualified access remains available; no bare-name contextual case lookup or enum search across unrelated types is selected. Collision handling with metadata .field remains open. See [enums and variants](enums-and-variants.md#inferred-case-names).
- Explicit enum backing types follow enum with a colon, and case values use `=`, as in `Status := enum : Float { Ready = 1.1; Busy = 2.2; Stopped = 3.3 }`. The colonless header is superseded. This selects Float backing-value support, without selecting implicit numeric conversions, physical layout, omitted-value numbering, or how backing values combine with payload cases. See [backing types and assigned values](enums-and-variants.md#backing-types-and-assigned-values).
- The enum backing-type clause and each assigned case value are independently optional, including mixtures of explicit and omitted values. A written backing type still requires colon. Backing inference/defaults and automatic case numbering remain semantic decisions; omission itself is selected. See [optional enum type and values](enums-and-variants.md#independently-optional-type-and-values).
- The three base pattern operations are bind (`name`), type match (`: Type`), and value match (`== expected`). Type/value tests introduce no name; `name: Type` composes binding and type matching. Literals are concise value tests. Structure and case patterns route components and test shape/tag identity without requiring whole-value equality. Complete operand, effect, and ownership contracts remain open; see [pattern primitives](pattern-bindings-and-tests.md).
- Pattern source placement and equality remain distinct: `if .Some(age) := source` binds its payload, while `if .Some(== expected) := source` tests the payload against an existing value. Ordinary expression == never introduces bindings, and `.Some(age) == source` is not a binding-condition spelling. Match arms and receivers already receive their input from their construct and do not add := merely to use the same pattern; see the [operator-placement audit](pattern-contexts.md#operator-placement-audit).
- Whole typed declarations and typed conditions use `name: Type = source`; `name: Type := source` is rejected. The := source form excludes an outermost typed binding, while type constraints inside structural patterns remain valid, such as `if .Some(age: Int) := source` or `(age: Int, name) := pair`. Direct typed patterns in match arms and receiver slots retain their separate contracts. This resolves the previously open typed-binding syntax overlap.
- Bare identifiers in patterns bind, independent of capitalization or an outer constant/type. Use `.None` for the absent Option case; bare None binds. Existing Some(value) payload constructor heads keep their explicit role, and ordinary expression uses of prelude None retain normal lookup. Bare `User` is therefore not a type-test shorthand. See [pattern bindings and tests](pattern-bindings-and-tests.md).
- Option pattern examples use `.Some(value)` and `.None` consistently as contextual case patterns. This uses existing selected syntax without banning the older named Some(value) payload head. An unguarded top-level `_` accepts remaining whole subjects and binds one to readable `_`; it is not an absent-case selector or a nonbinding discard. A component `_` binds its supplied component under the same ordinary rule.
- Tag-only enum patterns omit the complete payload-pattern list and introduce no payload binding: `if .Some := source` and `.Some { body }` in match test the same case. This applies to any payload-bearing case and nested case patterns. An unguarded tag-only arm covers every payload of its case under first-success selection. It does not construct a value without data, select partial/empty argument-list rules, or introduce filtering/dispatch in receiver contexts. See [tag-only patterns](enums-and-variants.md#tag-only-patterns).
- Match must support equality, conventional payload-free enums, enums with associated values, destructuring, and type checking/matching. Enum cases are not assumed to be separate types; plain enum support does not silently select integer conversion or representation rules. See [match pattern capabilities](match-patterns.md) and [enums and variants](enums-and-variants.md).
- Type matching composes with destructuring: `(x: Int, y: String)` can test and bind tuple components directly in a match arm or an `if` pattern; constructor payload patterns can contain such subpatterns. The whole pattern must match before its branch executes. This narrows without implicit conversion; complete ownership and nested grammar rules remain open. See [typed destructuring](match-patterns.md#typed-destructuring-selected-composition-rule).
- In partially annotated patterns, infer every unannotated binding from the input portions compatible with the entire pattern. Give it the corresponding concrete type or union, excluding impossible alternatives from all projections. Preserve composite alternatives rather than inventing combinations by independently widening their components. This rule concerns bound input values, not arbitrary unions of match-arm results; see [pattern binding inference](pattern-binding-inference.md).
- Whitespace outside token separation and literal data does not determine structure.
- Ordinary `/* ... */` comments nest; raw `/*# ... #*/` comments use matching hash fences and do not nest.
- Comments do not parse source text or insert item separators; missing closing delimiters are errors.
- Unicode identifiers are supported; the precise Unicode profile and normalization policy remain open.
- Fractional literals require a leading digit: write `0.5`, not `.5`; leading-dot context access remains distinct.
- `_` is an ordinary readable underscore-prefixed binding, not a separate wildcard. Every repeated binding name within a pattern shadows in recursive written order, including `_`; the last occurrence is visible without implying equality or changing an earlier binding's type. Source lookup precedes new bindings. This replaces the nonbinding-wildcard decision; see [pattern binding and shadowing](pattern-shadowing.md) and [underscore bindings and skips](wildcards-and-skips.md).
- Sequential local declarations may shadow earlier names in the same block, consistent with repeated pattern bindings. Resolve the ordinary initializer against the previous bindings before introducing the new names. Parameter/field/module declaration lists and recursive function initialization retain separate contracts. See [local shadowing and copies](local-shadowing-and-copies.md).
- A mutable declaration from an existing copyable record creates a shallow mutable copy. Every nested inline record is part of the outer value layout and is copied; reference fields retain targets and permissions, including existing mutable reference permissions. No recursive graph clone or universal unchecked resource-copy rule is selected. Fresh construction needs no redundant copy; general transfer, copy eligibility, cleanup, and alias rules remain open.
- An underscore-prefixed name, including _, _user, or _left, remains an ordinary readable name and explicitly permits nonuse without unused-name warnings. This applies to locals, pattern/parameter/receiver bindings, and declared fields where those diagnostics apply. It does not alter visibility, initialization, ownership, type constraints, or separate required-use/error-handling rules. See [unused-name intent](unused-name-intent.md).
- Explicit semicolons separate ordinary items; there is no automatic insertion.
- Complete block constructs end their items without requiring semicolons; trailing semicolons are optional and allowed, including for declarations initialized directly by block constructs. This supersedes the earlier prohibition.
- Continuing a block construct's value with an operator, call, member access, or indexing requires parentheses around that construct.
- Attached `else`, `then`, and `finally` clauses belong to the complete construct before its item ends.
- Extra semicolons are harmless, including after complete block items, and do not become empty result-producing statements. Trailing commas in comma-separated lists are optional and allowed; required separators between ordinary items/list elements remain significant.
- Final expressions produce block results; final declarations/assignments produce `Unit`.
- Explicit `Unit` should be supported as a value.
- Since `Unit` has one inhabitant, the selected universal zero rule makes `zero(Unit) = Unit`. The user proposes zero-sized physical storage; calling convention and foreign ABI lowering remain separate representation details. See [Unit](unit.md) and [universal zero initialization](zero-initialization.md).
- `:=` declares with inference; `: Type =` declares with annotation; `=` assigns.
- Inferred declaration prefixes are mut, var, or var mut. Typed forms use name: mut T for writable data access, with var before the name when rebinding is needed. The former mut name: T and var mut name: T spellings are superseded. Inferred mut var and repeated modifiers are rejected; see [mut placement](mut-qualifier-placement.md).
- Typed mutation parameters use fn(user: mut User) { ... }; the full method-receiver notation remains open. Inferred declarations retain mut user := expression. This changes placement without changing access or argument-passing semantics.
- Whole-binding `=` and compound updates require `var`; field/element updates require `mut` and the target's other permissions.
- Assignments are not general expressions or chained value assignments.
- Function result annotations use `:`, not `->`.
- Uniform name bindings can hold function and type definitions.
- Field aggregates use record, as in `Student := record { name: String; grade: Int; }`, replacing the earlier type-body record sketch. Declared field types use colon; construction supplies predefined fields as field = expression. Named patterns use inferred braces and destinationPattern = sourceField; the previous reverse direction is superseded. field == expected compares without binding, while field: Type type-tests and binds that same-named field. Type-only testing is : Type = sourceField. Construction may name its type explicitly or omit it when a unique expected record type is known, including annotated bindings and nested record fields. Distinct identity per declaration is selected. Complete inference/brace disambiguation, generic instantiation, visibility, and memory remain open; see [records](records.md) and [aggregate clauses](aggregate-patterns.md#named-field-clauses).
- Empty contextual record initialization is selected: profile: Profile = {} constructs a record and applies its declared-default policy. Empty executable bodies, including fn() {} and _ {} match arms, still produce Unit. Expected record result types must not silently reinterpret body braces as data. The grammar must express initializer and body roles explicitly; see [initialization modes](record-initialization.md#2-two-initialization-modes).
- A simple typed declaration may omit its initializer: value: Type; immediately zero-initializes, equivalent to value: Type = 0. Var value: Type; uses the same zero initialization and exposes the writable storage contract var Type; reading still produces Type. No uninitialized state, deferred first write, source-free destructuring, or optional function argument is introduced. Both zero forms use a valid language-defined all-zero representation for every type and bypass declared field defaults. See [zero initialization](zero-initialization.md).
- Explicit contextual zero initialization uses literal 0. Inferred 0 remains Int, an integer variable is not converted to a record, and nonzero integer literals are rejected for record initialization. The separate = {} form applies declared defaults. Initialization mode does not itself grant var/mut permissions.
- The four-form direction is selected: value: Type; means implicit zero, = 0 means explicit zero, = {} means declared defaults, and = ? explicitly requests uninitialized storage. The final form is a special construction/storage marker for simple typed value declarations, not a usable unknown value. Full initialization-state, first-write, eligible-layout, and allocation/cleanup contracts remain open. Reserve(), {?}, ?=, and ?Type are unselected alternative spellings, not synonyms. See [reserved storage](reserved-storage.md).
- Whole-value first initialization of an explicitly reserved binding uses = without var, once per execution path. Multiple source sites in mutually exclusive branches are allowed; every path reaching ordinary value use must have initialized the binding. Missing branches are compile errors, not implicit zero/default construction. Later whole-binding replacement requires var. The first successful write installs the valid value; partial/callee construction and cleanup remain open. See [first initialization](first-initialization.md).
- Large arrays/buffers are the main motivation for explicit uninitialized reservation. Storage exists; payload bytes are unspecified, not null/missing storage or readable random values. Avoid a mandatory preliminary zero pass before bulk filling. Element-initialization syntax, coverage/prefix tracking, allocation policy, and partial cleanup remain open; see [reserved arrays](reserved-storage.md#main-use-case-large-arrays-and-buffers).
- Initialization requirements describe source semantics, not mandatory physical stores. In var x: User; x = make_user();, the optimizer may omit unobservable zero stores and use untouched destination storage internally while preserving all defined observations and required cleanup, including exits before replacement. Every type has a valid all-zero representation regardless of optimization; this does not expose a source-level uninitialized value. See [semantic initialization versus physical writes](memory-and-performance.md#semantic-initialization-versus-physical-writes).
- Each record type declaration creates a distinct type, including unnamed inline declarations, even when field shapes are identical. Convert through explicit destination reconstruction, subject to visibility and ownership. Contextual construction and headless deconstruction do not introduce implicit structural assignment. Reuse one shared record type declaration when different fields need the same type; see [record type identity](record-type-identity.md).
- Named transparent aliases use Alias := type TypeExpression for both simple and composite types. The keyword covers the whole right-hand type expression, introduces no nominal wrapper, and is not optional in alias definitions. Ordinary value bindings remain unchanged; name capitalization never chooses their kind. See [type aliases](type-aliases.md).
- Plain unions ignore member order, flatten nested plain unions, and remove duplicate resolved type identities, including transparent aliases. A | (B | A) is the same type as A | B. Distinct record declarations and enum cases retain identity; Option/Result and whole product alternatives are not flattened or redistributed. Match-arm order remains source order. See [union normalization](union-normalization.md).
- An existing value of a listed member type is admitted to a plain union automatically, without a cast or explicit case wrapper. Using an arbitrary union value as a particular member requires checked narrowing. Resolve aliases/normalization before exact membership; do not infer numeric conversions, equal-shaped record conversion, or interface implementation. See [union membership](union-membership.md).
- A plain union widens automatically to another when every normalized source alternative is an exact destination member. Preserve the active member's identity; no numeric conversion, record reconstruction, interface conversion, or recursive container/Result conversion follows. Reverse assignment needs checked narrowing when the source permits uncovered alternatives. Ownership, permissions, and layout remain separate; see [union widening](union-widening.md).
- The [reference comparison](union-membership-comparison.md) distinguishes direct unions (Scala/TypeScript), discriminated sums (Odin/V), explicit named cases (Rust/Zig/Swift), common-root sealed hierarchies (Kotlin/Dart), C++ variant construction, and Python/Lua dynamic behavior. It supports the chosen admission ergonomics without importing their nullable defaults, casts, hierarchy obligations, or representation policies.
- Early returns are encouraged.
- Common field reads through a plain union require a readable field on every possible alternative. The result is the normalized union of field types, including duplicate removal and order independence. Missing or inaccessible fields reject the projection; they are not bottom-type members to discard during normalization. Record identity stays nominal. Methods and full flow/ownership rules remain separate; see [union field reads](union-field-reads.md).
- Field writes through a plain union must be accepted by every possible target field, with mut and writable access. For P.field: C | D and Q.field: C | E, reading through P | Q produces C | D | E but only C can be written without narrowing. A standalone variable declared C | D | E can accept any member; the projected read type does not replace each parent's storage contract. See [union field writes](union-field-writes.md). Explicitly presentable access contracts are investigated in [union values and access](union-values-and-access.md); their public notation and first-class status remain proposals.
- Ordinary `Result` success is implicit when an appropriate contract is expected; errors are explicit.
- A var-qualified function parameter provides temporary access to the caller's location. Assignment through it replaces the supplied caller variable or field. The explicit call grant replace(var value) requires an already writable location; a whole binding must be var. Var alone grants no held-data mutation. This selects neither public pointers/general reference values nor a complete borrowing model. Ordinary read-only parameter semantics, aliasing, and full access compatibility remain open; see [var parameters](slot-parameters.md).
- Type-side var is the canonical replacement qualifier, superseding slot in signatures, explicit call grants, and access summaries. Fn(param: var T) receives writable caller storage; local-only fn(var param: T) headers are omitted. Use var param := param in the body for local working state. The shorthand fn(param: var) requires an inferable value type; general parameter inference remains open. See [var access](var-access-qualifier.md).
- A mut-qualified parameter requires an explicit mut argument grant, as in rename(mut userVar). The caller must already possess mutable access, and writes affect that supplied data rather than a silent detached copy. Ordinary read-only inputs grant neither writable caller-data access nor caller replacement. See [caller grants](caller-mutation-grants.md).
- Local-only var parameter headers are retired: use local declarations and sequential shadowing inside a normal parameter's body. Var count := count preserves the input as the working value; var count := 5 initializes that working value to 5.
- Within an access contract, var marks accepted replacement alternatives: A | var B | C reads A/B/C and accepts B on a permitted write. It supersedes mut for this marker; declaration var/mut keep their separate meanings. Grouped scope distributes within one contract: var (A | B) is equivalent to var A | var B. A var binding of A | B has that whole-binding replacement summary, independently of mut. Prefix scope preserves the full denotation of a transparent alias operand. Full access declaration grammar, contract boundaries, and first-class access types remain open. See [var access qualifier](slot-access-qualifier.md).
- Fallible type notation is `T ! E`; `T!` means exactly `T ! Error`, declaring the general recoverable error contract. A plain `T` declares no recoverable failure. Refined error types remain available; `!T` is not an alternate spelling. Type and expression contexts distinguish a fallible type from postfix propagation without whitespace semantics.
- Multiline strings and adjacent literal joining are desired.

### Operators

- Use `and`, `or`, and `not`.
- Use `==` for equality; express inequality through negation.
- Comparison binds more tightly than `not`, followed by `and` and `or`.
- `<`, `<=`, `>`, `>=`, and `==` form comparison chains at one precedence level, checking adjacent operands with strict `Bool` results.
- Chain operands evaluate at most once from left to right; a false comparison skips later operands and comparisons. All pairs must type-check.
- Mixed comparisons and changes in direction use the same adjacent-pair rule; `not` applies to the complete chain unless parentheses specify another grouping.
- Ordinary operator operands evaluate left to right after grouping. Calls evaluate the callee first, then supplied argument expressions in source order, then invoke the callable. Short-circuiting skips unneeded expressions.
- Assignment selects its target once before the right-hand side; compound updates read its current value before their right operand, then compute and write the result. Alias and lifetime rules still need formalization.
- `?=` and `!=` have no selected meaning in the current design.
- Supported `op=` updates use defined underlying operations and evaluate the target once.
- `/` is fractional division; `//` performs integer division on integer operands, with `//=` as its update form. Positive examples are `7 / 2` yielding `3.5` and `7 // 2` yielding `3`.
- Ordinary integer division uses operator syntax without mandatory named rounding helpers or floating-point conversion. Integer `//` rounds toward negative infinity, including for negative divisors; `-7 // 2` and `7 // -2` both produce `-4`.
- Integer `%` is paired with the floor quotient so that `a == b * (a // b) + (a % b)` holds mathematically. A nonzero remainder has the divisor's sign. `//=` and `%=` preserve those rules; numeric representation, noninteger remainder, conversion policy, and operator failure contracts remain open.
- `//` is not a line-comment opener. Outside comments and strings, slash operators use longest-token recognition, including `//=` as one token.

### Conditional and loop direction

- One `if` form works for actions and values; branch braces establish ownership.
- One `loop` keyword handles Boolean, iterable, and unconditional sources.
- Remove post-condition loop syntax; use inner conditions and explicit exits.
- Loop headers allow one optional item identifier introduced by as; colon and header patterns are retired. Count/value receiver lists, receiver-slot shadowing, and header tuple patterns are retired. The item name denotes the same current element as .item; destructuring and refutable selection belong inside the body. See [item naming](loop-receivers.md).
- Loop metadata supplies .item, .index, .count, and .value. Index is zero-based traversal position, independent of source keys/positions and reversal/step. Count counts entered iterations. Item/index are readable during active iterations and as last-visited metadata in then if an iteration occurred, not in source/condition evaluation. After zero entries, then exposes typed zero placeholders for .item and .index, with .count == 0 distinguishing them from an actual first entry. Count/value are available before the first condition, in the body, and in then. Retain last-item state for completion only when observable use requires it.
- Loop .value replaces .acc and automatic Option accumulators. It has a static body-result type and is zero-initialized before iteration; tail completion, continue value, or break value commits; plain continue and bare break preserve. No value_or helper or previous receiver is required. See [loop value](loop-value.md).
- Do not inject implicit ordinary names such as `it` or `acc`.
- Direction and stepping should be source/range capabilities rather than more loop keywords.
- Plain continue preserves .value and advances; continue value commits early and advances. `continue @tag [value]` applies the same rule to an explicitly named enclosing loop, committing to that loop before advancing when a value is supplied. Bare break preserves .value and runs then. Break value commits its T operand, stops the nearest loop, and runs then. `break @tag [value]` applies the same loop exit to an explicitly named enclosing loop, while untagged break still targets the nearest loop even if it has a tag. A tagged return supplies T to its named target and runs that target's then if present; constructs exited on the way skip their own then blocks. Target support is sparse: break/continue target loops; tagged return targets loops, ifs, general result blocks, or functions; plain return targets the nearest function/closure. Unsupported operation–target pairs are invalid.
- Loop completion uses receiverless then { ... }. Its current context is the owning loop, tagged or untagged: .count and .value are available directly. The tail expression supplies the completion result, including Unit; the earlier completion-receiver and action-preservation distinction is superseded. Nested contexts retain no outward field search.
- Without then, normal completion returns final .value; with then it returns that block's tail expression, and then {} returns Unit.
- Loop type inference uses body constraints and destination-side expected types. A Long destination can constrain .value, including a body consisting only of .value. With then, expected final type R constrains body type T only through actual type relationships. Numeric promotion/casts remain the arithmetic contract; see [loop inference](loop-type-inference.md).
- Concise optional search loops should not require redundant `None` bodies or `else { None }`.

### Tags

- A tag is an explicit typed construct context, not a global loop object.
- Put it before the construct: `@name loop ...`, `@name if ...`, or `@name { ... }`.
- Construct kind determines metadata and permitted operations.
- Tags follow lexical shadowing; an inner tag may reuse a name.
- Loop `.field` shorthand refers only to its current loop context, with no outward fallback; within a conditional, use an explicit loop tag. Conditional `.value` requires `@tag.value` and is available only inside the conditional's attached `then`; ambiguous leading-dot metadata reads are rejected.
- `@name.field` explicitly selects a named context.
- A loop's tag remains accessible in its attached completion block. Final count and typed value are readable there; other metadata must be valid for that phase. This scope does not keep iteration-local items/references alive automatically. See [completion tag access](unified-loop-completion.md#access-through-the-owning-loop-tag).
- `return @tag [value]` exits a named construct; its payload supplies the target's pre-then T, and the target's `then` runs to produce R if present. Constructs exited on the way skip their `then` blocks. Without a target `then`, T is the target result; an omitted payload is `Unit`.

## Contracts to settle next

### 1. Loop contribution and construct-result inference

Define body-result type T and final construct-result type R independently. The .value storage has T and is zero-initialized; it is not automatically Option<T>. A body whose only value-producing path is `.value` is circular and remains ambiguous without an independent type constraint; the no-contributor `Unit` default does not resolve it. Complete inference for last-value loops, Unit actions, targeted-result-only search loops, and optional results without nested wrapping. Implement a coherent inference specification for the selected no-then .value rule and any future nonzero initialization mechanism.

When a loop has no contributing path and nothing else constrains T, T defaults to Unit; an expected type can override that default. Plain continue and bare break do not themselves contribute Unit; an action body that normally completes with Unit does. A `then` result independent of `.value` determines R but leaves T at its default. See [noncontributing loop paths](loop-type-inference.md#loops-with-no-contributing-path).

For conditionals, when no normally completing branch constrains T, T defaults to Unit; an expected type can override it. The missing-final-else path returns zero(T). That is a real conditional result: when the `if` is the final expression in a loop body, the loop commits it and may replace its previous `.value`. This differs from `continue`, which advances the loop without contributing. Inside the `if`, use an explicit loop tag to read the enclosing loop's `.value`.

### 2. Completion hooks and abrupt exits

For a typed panic that matches a handler in the same scope as its `finally`, the handler recovers first and that scope's `finally` runs once as it exits. If the panic escapes toward an outer matching handler, exited inner scopes run their applicable `finally` blocks first.

The single receiverless `then` is selected for loops and complete conditional chains. A conditional `then` processes the selected branch/zero result T into final R, with read-only `@tag.value` available only in that block. `then` names result processing; reserve `finally` for cleanup that preserves a pending result or exit. When both hooks are attached to a loop or conditional, `then` completes before `finally` runs cleanup as the construct exits. Normal completion and a return targeting the conditional supply T and run its `then`; a return to an outer target skips the inner conditional's `then`, while applicable cleanup still runs on exit. Propagated errors and unhandled panics provide no conditional T and skip result processing; applicable cleanup runs while leaving. During language-managed panic propagation, exited-scope `finally` blocks run before an outer matching handler. Exact attachment syntax/scope remains open. Loop count and typed value remain available from the owning context.

The user selected cleanup-only `finally`: no implicit pending-outcome receiver, recovery, or result/exit transformation. If cleanup completes normally, preserve the pending result, control-flow exit, propagated recoverable error, or typed panic. On normal loop/conditional completion with both hooks, `then` completes before `finally`; the cleanup result does not replace the construct result. If any failure is pending, preserve it as primary and retain every cleanup failure as secondary. If only normal completion is pending, the first cleanup failure becomes primary and cancels that completion. A same-scope handler recovers a matching typed panic before that scope's `finally` runs once on exit, so a later cleanup failure is primary. Still define the aggregate carrier, how typed handlers inspect or consume its components, which scopes can attach `finally`, and no-handler/hard-abort behavior. A reusable failure-aggregation type or mechanism for other multi-failure cases is a separate open design question; see [failure aggregation](finally.md#failure-aggregation-and-open-design).

The selected policy prevents a cleanup failure from hiding the failure that caused cleanup to run. For example, when writing fails with `DiskFull` and closing then fails with `CloseFailed`, callers must still see `DiskFull` as the primary failure and retain `CloseFailed` as secondary. No concrete aggregate type, collection shape, syntax, or runtime allocation strategy is selected. A general `Error` accumulator could serve other aggregation cases, but a recoverable-error-only type must not erase the separate typed-panic channel; any shared carrier must preserve each component's category and match behavior. The user selected declaration-ordered member-wise handling: each typed handler consumes matching pending members, and the next clause sees the remainder. Reordering handlers is observable; for `A & B`, both matching clauses run in their written order, and the last matching handler's value is the recovered result if all members are consumed. A surviving remainder propagates. The aggregate carrier and duplicate-member consumption remain open.

Break value is selected as commit-and-stop followed by normal completion. Tagged-return behavior is selected: its payload satisfies T and the named target's `then` produces R when present; intermediate `then` hooks are skipped. Labeled continue is selected: an optional value commits to the named loop before it advances; intervening constructs skip their `then` blocks.

### 3. Optional item naming and initialization

As is selected for one optional item name, with colon retired. There is no remaining count/value receiver list or header tuple pattern. Define any future nonzero value initialization without reviving the retired receiver/seed forms accidentally.

### 4. Context phase rules

Specify initialized fields during source evaluation, conditions, bodies, hooks, and cleanup. A conditional's internal result exists before selection and is readable as `@tag.value` only inside its selected post-selection `then`; branches and conditions cannot read it through metadata. Conditional condition metadata is hidden for simple conditions and `else if` chains. Ambiguous leading-dot metadata reads are rejected, without outward fallback. Keep `then`'s result-processing role distinct from cleanup-only `finally`; when both hooks are attached, `then` precedes `finally`, which does not recover failures. A tagged return to the conditional enters its `then`; a return to an outer target skips it while cleanup still runs on exit. Propagated errors and unhandled panics supply no conditional result. Language-managed panic propagation runs applicable exited-scope `finally` blocks before an outer matching handler; exact attachment syntax/scope remains open. Define whether an untagged expression block establishes a new current context. Ordinary body braces do not add a wrapper context.

For an `if` chain, distinguish the selected branch from conditions that were never evaluated. Do not represent an unevaluated condition as if it had evaluated false.

### 5. Type-system and ownership foundations

Choose generics, nominal identity, interfaces, variance, borrowing/moves/copies, shared values, closure captures, and type-level values. Define general type/value namespace rules; the Unit-specific `Unit` type and expression spellings are selected, while broader name resolution remains open.

Binding reassignment (`var`) and held-data access (`mut`) are independent. Complete method notation and receiver/parameter passing rules, define how read-only access propagates, and decide whether a stronger frozen-value guarantee exists. Mutation is marked on affected receiver/parameter bindings, without an additional function-level marker. Do not infer purity or global immutability from a read-only receiver.

### 6. Standard library and project boundaries

Specify range/iterator capabilities, invalid dynamic stride handling, collection ownership, I/O failure, import/export grammar, package identity, and build behavior.

### 7. Numeric arithmetic

Integer `//` uses floor rounding and integer `%` is its paired remainder. The user selects typed panics, not returned `Result` errors, for basic arithmetic faults. Individual-operation recovery uses target-level `else` with typed filters: a matching panic can be handled locally, unmatched panics propagate, and returned errors remain explicit. Define exact fault cases, including zero divisors and unrepresentable fixed-width quotients, and complete floating-point representations, mixed numeric operations, noninteger remainder, and conversion policy independently of the selected division semantics. See [arithmetic fault boundaries](arithmetic-faults.md) and [division](division.md).

### 8. Typed recovery syntax and arithmetic failure boundaries

Local recovery is required for individual operations, including arithmetic panics and returned function errors. Returned recoverable errors use postfix `!` propagation or `else` recovery with optional and typed receivers; ordinary calls can retain their Result as data. Recovery forms `T | D` from success and normal fallback types. Every escaping recoverable error must fit an explicitly declared error contract: `T ! E` is refined and `T!` explicitly means `T ! Error`. Define the general Error contract, generic error contracts and conversion, union composition and narrowing, representation, complete expression precedence and nested-operand scope, and ignored-outcome diagnostics. Arithmetic's panic channel and typed-filter recovery are selected; language-managed panic propagation unwinds applicable `finally` blocks before an outer matching handler. Exact triggers, broad receiver typing, capture boundary, and hard-abort policy remain open. See [result and errors](result-and-errors.md), [fallible types and error composition](fallible-types-and-error-composition.md), [propagation and call chaining](propagation-and-chaining.md), and [panics](panics.md).

### 9. Pattern matching after underscore unification

Ordinary readable underscore bindings and ordered shadowing within patterns are settled. The next pattern review should distinguish binding from existing-value equality and type-only tests. Then complete recursive pattern grammar, including aliases, whole-value/nested colon syntax, and rest capture; define rebinding across and operands, binding-producing or/not, and stability of narrowed names under mutation.

The [focused review](pattern-bindings-and-tests.md) compares Rust, Python, Dart, Swift, Kotlin, Odin, Zig, and V. Bind (`name`), type match (`: Type`), and value match (`== expected`) are now selected base operations, alongside explicit `.None` case spelling. Complete operand/effect, recursive composition, and type-refinement contracts.

Loop headers now bind only one optional item name; no receiver pattern needs an irrefutability rule. Parameter, recovery, and completion receiver policies remain to confirm. Complete coverage and fallback rules, enum-case/metadata collisions, stored Result payload extraction, and ownership/lifetime contracts. These are separate from underscore unused-name intent; see [pattern binding and shadowing](pattern-shadowing.md) and [pattern context review](pattern-contexts.md#review-findings-and-decisions-to-settle-first).

## Superseded suggestions

- Keeping slot as a separate source keyword for caller replacement. Type-side var now carries the same contract, and explicit var call grants preserve visibility. The earlier rejected left-side fn(var param: T) substitution and local-only header proposal do not define this later type-side form.

- Typed mutation prefixes before names, including mut user: User and fn(mut user: User). Use user: mut User in annotated declarations/parameters; inferred mut user := expression remains valid.

- Bare None as an absent-case pattern or a special prelude-constructor exception. Use `.None`; bare pattern identifiers bind.
- Bare `User` as a type-only arm selected through type-name lookup. Use the selected marked `: User` type-only pattern instead.

- Indentation or newlines as statement/body delimiters.
- Optional unblocked function, conditional, and loop bodies.
- The earlier pattern-if match guard separator; match arms use and chains instead.
- Provisional LiteScript `if let` headers or mandatory `case`, `=>`, or `then` separators in match arms.
- `do/end`, `then/endif`, or specialized `endfn/endloop` as the selected block system.
- Mandatory parentheses around every conditional as the chosen source/body divider.
- Post-tested loop syntax and a separate required `loop if` spelling.
- Treating every loop receiver as an automatic metadata tuple.
- Changing the supplied value based on whether a pattern is a simple name or tuple.
- Requiring `.with_state()` or a separate `with` clause just to access ordinary loop metadata.
- Implicit `it`, global `loop.field`, or a current-context lookup that searches outward.
- A prohibition on nested tag shadowing.
- Suffix tags or `name: construct` as the current tag placement.
- Mandatory `Ok(...)` on normal success paths.
- Automatic extraction of success and propagation of recoverable failure from an ordinary call without an explicit caller choice.
- Prefix `try` or postfix `?` as recoverable-error propagation aliases; postfix `!` is selected.
- Requiring a `?` marker to retain a call's Result outcome.
- Silently inferring additional escaping recoverable errors outside a function's declared error contract.
- Requiring every fallible declaration to use general Error instead of allowing refined error contracts. `T!` deliberately chooses general Error; `T ! E` retains a refined contract.
- Mandatory trailing `None` or redundant empty clauses for simple searches.
- Semicolons suppressing final-expression results.
- Requiring a semicolon after a complete block item, or the earlier prohibition on allowing one. Trailing semicolons are now optional and allowed.
- Continuing an unparenthesized block value across its item boundary through an operator, call, member access, or indexing.
- Treating `_` as a nonbinding wildcard or prohibiting reads of it. It is an ordinary underscore-prefixed name; ordered shadowing replaces the intermediate wildcard decision.
- Requiring unique binding names within a single pattern or prohibiting sequential local shadowing in the same block. Later pattern names and later local declarations shadow earlier ones; parameter/field/module declaration lists retain separate rules.
- `_ = value` as special discard syntax. It is ordinary assignment requiring an existing var binding with a compatible type.
- Granting writable owned fields through `var` alone; `mut` is required explicitly.
- Requiring an additional function-level mutation marker beyond explicit `mut` receiver/parameter contracts.
- Rejecting comparison chains merely to simplify the grammar, or treating them as ordinary left-associated binary comparisons.
- Requiring verbose named division helpers as the ordinary interface for integer-only arithmetic; `//` and `//=` are selected.
- Truncation toward zero as the meaning of integer `//`, or a mismatched truncating remainder for integer `%`.
- `?=` equality or conventional `!=` inequality as currently selected operators.
